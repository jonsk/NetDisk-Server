# Server-com 代码阅读指南

> 适用版本：Server-com（开源版 / Community）· Go 服务端单二进制网盘
> 阅读对象：需要读懂、排查、二次开发这份代码的工程与运维同学。
> 本指南讲"代码是怎么组织的、数据怎么流动、想改 X 去哪儿找"，不逐行讲算法。
> 逐模块验收与开发红线见同目录 `功能清单与开发任务清单.md`；权威设计见 `D:\WorkSpace\GO\Doc\网盘系统架构设计文档.md`（V3.0）。

## 1. 这个仓库是什么

`Server-com` 是一个企业网盘**后端服务**，用 Go 写成，最后编译成**一个可执行文件**（单二进制）。

它对外提供四类能力：

| 能力 | 说明 | 主要入口 |
|---|---|---|
| REST 管理/文件接口 | 后台管理、文件增删改查、下载、分享 | `/api/v1/*` |
| TUS 断点续传上传 | 大文件分片上传 | `/tus/*` |
| WebDAV | 桌面端挂载盘（兼容文件协议） | `/webdav/*` |
| SSE 实时同步 | 推送"文件变了"给客户端，客户端再拉增量 | `/api/v1/events` |

它**不**负责：HTTP 反代（Nginx）、前端页面（`web` 仓库）、桌面客户端（`desktop` 仓库）。这三个是独立仓库或外部组件。

> 一句话：这个仓库 = 一堆 Go 包 + 一组命令 + 迁移脚本 + 部署物料，最终产出一个 `netdisk` 二进制。

## 3. 命令（cmd/）—— 每个都是独立小程序

`cmd/` 下有 8 个目录，各自是一个 `main` 程序：

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| **netdisk** | **主服务**，唯一面向生产的进程 | `systemd` 启动的那一个 |
| **migrate** | 数据库迁移 | 部署时 `go run ./cmd/migrate up` |
| **passwd** | 账号运维：建用户 / 重置口令 / 启停用 | 运维手工操作账号 |
| **probesmoke** | 端到端探针：真实 HTTP 打一遍登录→上传→下载 | 开发期自测 |
| **devdb** | 本机开发/测试库维护 | 开发者本地用 |
| **depsguard** | 架构门禁：检查"内核包不得依赖 HTTP 层"等 | CI 静态检查 |
| **testsgate** | 集成测试门禁：确认测试真的跑过 | CI |
| **coveragegate** | 覆盖率门禁：按包统计语句覆盖率 | CI |

生产环境只关心前两个：`netdisk` 和部署时用到的 `migrate`。其余是开发/CI 辅助。

## 4. internal/ 包地图 —— 代码在哪、干什么

36 个包按职责可分五层。理解分层是读懂本仓库的关键：**HTTP 层只做"收请求、调服务、回响应"，业务逻辑在服务层，真正读写数据库在 repo 层，最底层是数据库/Redis/磁盘。**

### 4.1 入口与 HTTP 层（你在这个仓库第一个接触的）
| 包 | 职责 |
|---|---|
| **api** | **路由总装配**。所有 URL↔处理函数 的映射都在 `api.go`。几乎所有"这个接口调谁"都能在这找到 |
| **middleware** | 中间件链：请求ID、真实IP、结构化错误、日志、崩溃恢复。请求穿过的"安检关卡" |
| **apierr** | 统一错误封装（HTTP 状态码 + 业务码 + 中文文案） |
| **webui** | `/admin` 后台前端静态资源入口（embed 进二进制，Nginx 不再托管） |
| **reqctx** | 把"当前登录用户"（Actor）放进请求上下文的工具 |

### 4.2 认证与权限
| 包 | 职责 |
|---|---|
| **auth** | JWT 签发/校验（令牌本身，无状态） |
| **authsvc** | 账密登录/刷新/登出的业务编排（查库、验密、锁定、token 版本联动） |
| **webdavauth** | WebDAV 的 Basic 认证通道 |
| **credentials** | 口令哈希（bcrypt 类）与强度策略 |

### 4.3 业务服务层（每个对应一类业务，最值得细读）
| 包 | 职责 |
|---|---|
| **usersvc** | 后台用户管理（建号/启停用/角色） |
| **orgsvc** | 组织架构（部门树） |
| **spacesvc** | 空间（个人空间/团队空间）与成员协作 |
| **filesvc** | 文件元数据（列表/改名/移动/删除/建目录） |
| **uploadsvc** | 上传任务创建、ticket 校验、TUS 数据面 |
| **fastupload** | 秒传的"持物证明"挑战 |
| **finalize** | **定稿**——所有上传最终写入的唯一入口，全网最关键的写路径 |
| **sharesvc** | 分享链接（系统唯一的免登录出口） |
| **dirops** | 目录级异步任务队列（超大目录操作后台跑） |
| **quotareconcile** | 配额对账与漂移告警 |
| **patrol** | 对象巡检：扫磁盘找泄漏/孤儿文件 |

### 4.4 领域模型与同步
| 包 | 职责 |
|---|---|
| **model** | 与数据库表严格对应的实体（struct） |
| **namepolicy** | 文件名的唯一裁判（校验合法性、长度、深度） |
| **objlock** | 对象级锁（写同一文件时的互斥纪律，防止并发覆盖） |
| **syncfeed** | 变更流（谁改了什么）的写读 |
| **syncsse** | SSE 事件通道（推送给客户端） |

### 4.5 基础设施（大多数时候你只需知道它存在）
| 包 | 职责 |
|---|---|
| **config** | 配置加载（yaml + 环境变量） |
| **db** | PostgreSQL 连接池与事务 |
| **cache** | Redis 封装与键命名规范 |
| **ratelimit** | 基于 Redis 的限速 |
| **repo** | SQL 仓储层——**所有 SQL 都在这里**，是"看数据"的入口 |
| **storage** | 本地磁盘对象存储（内容寻址，文件按哈希存放） |
| **migrate** | 数据库版本迁移（goose） |
| **obs** | 结构化日志（slog） |
| **lifecycle** | 对象生命周期状态机 |
| **condreq** | HTTP 条件请求（If-Match/If-None-Match，乐观锁） |
| **webdavfs** | WebDAV 支持的底层文件视图 |

> **阅读速查**：想改"某个 HTTP 接口"→ 找 `internal/api/api.go` 的路由行 + 对应 `handlers_*.go`；
> 想查"数据库怎么读写"→ 找 `internal/repo/`；
> 想找"上传的最终落盘"→ 看 `internal/finalize/`（唯一写路径）。

## 5. 启动装配 —— 服务怎么"拼"起来的

一切从 `cmd/netdisk/main.go` 开始。按注释里的编号步骤，装配顺序就是：

1. **配置**：默认值 ← yaml ← 环境变量（后覆盖先）
2. **校验**：一次性打印全部问题，有问题就拒绝启动（fail-fast）
3. **PostgreSQL**：连库、跑迁移
4. **Redis**：连不上就拒绝启动（认证/限速都依赖它）
5. **令牌管理**：初始化 JWT 签发、Redis、限速器、各类业务服务
6. **HTTP 服务**：把 `internal/api` 装配的路由挂到端口上，启动监听

这个文件是"依赖注入"的地方——**在哪里 new 了哪些服务、传了哪些依赖，全在这一个文件里**。想理解"某个服务是怎么被组装出来的"，读它；想给系统加一个依赖，也改它。

## 6. 一次请求怎么走（理解流动就理解了这个仓库）

以"用户登录后请求文件列表"为例，链路是：

```
        ┌────────────────────────────────────────────┐
        │  Nginx：HTTPS 终结、反代、来源 IP 透传       │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  middleware 中间件链（internal/middleware） │
        │  requestID → realIP → structuredErrors →   │
        │  logging → recoverer（崩溃兜底）            │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  api 路由（internal/api/api.go）            │
        │  鉴权(auth) → 限速(ratelimit) → handler    │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  handlers_*.go  解析参数、调用服务          │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  业务服务层（filesvc/uploadsvc/...）         │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  repo 层：「唯一 SQL 的地方」→ PostgreSQL    │
        │  storage 层：读写磁盘对象                    │
        └────────────────────────────────────────────┘
```

**加粗记住这句**：`api 层管"对外的样子"，`repo` 层管"和数据库打交道"，中间的服务层管"业务规则"。分层越清楚，改一处就只影响一处。

## 7. 配置怎么管理

看 `deploy/config/config.example.yaml`（配置示例，最权威的字段清单），以及 `internal/config/config.go`（加载逻辑）。

- 配置来源优先级：**代码默认值 < yaml 文件 < 环境变量**。
- **敏感项（密码、密钥）只走环境变量，永不进 yaml**。例如 `NETDISK_DB_PASSWORD`、`JWT_SECRET`、`NETDISK_REDIS_PASSWORD`。
- 配置大块包括：`server`（端口/代理）、`database`、`redis`、`jwt`（令牌有效期）、`policy`（配额/深度/大小上限）、`patrol`（巡检）、`webui`（后台前缀）、`storage`（存储根目录）、`log`、`rate_limits`（限速）。
- 启动时会校验；某个限速全 0、存储目录不可写等会被拦下来。

> 运维小贴士：改配置 → 编辑 yaml 或环境变量 → 重启 `netdisk`；**改前端要重编 Go 二进制**（因为页面 embed 进去了），只重启进程是不够的。

## 9. HTTP 接口速览

所有路由集中在 `internal/api/api.go`。按功能分组（省略鉴权细节）：

| 分组 | 示例路径 | 说明 |
|---|---|---|
| 健康 / 版本 | `GET /healthz`、`GET /api/v1/version` | 探活、版本协商（无需登录） |
| 认证 | `POST /api/v1/auth/login` / `refresh` / `logout` | 账密登录与令牌续期 |
| 我的信息 | `GET /api/v1/me` | 当前登录用户 |
| 文件 | `GET /api/v1/files`、`GET /api/v1/files/{id}/content` | 列表、下载（支持 Range） |
| 文件写操作 | `PATCH /api/v1/files/{id}`、`DELETE /api/v1/files/{id}`、`POST /api/v1/files/dirs` | 改名、删除、建目录 |
| 上传 | `POST /api/v1/upload/create`、`/tus/*` | 创建上传任务 + TUS 分片上传 |
| 秒传 | `POST /api/v1/upload/{id}/finish` | 持物证明通过后秒传定稿 |
| 编辑锁 | `POST/GET/DELETE /api/v1/files/{id}/lock` | 文件协同编辑锁 |
| 分享 | `POST /api/v1/shares`、`GET /api/v1/shares/{token}/meta` | 分享链接（免登录下载） |
| 空间 | `GET /api/v1/spaces`、`POST /api/v1/spaces` | 我的空间、建空间 |
| 组织/用户管理 | `/api/v1/admin/departments*`、`/api/v1/admin/users*` | 后台管理（需管理员） |
| 同步 | `GET /api/v1/events`（SSE）、`GET /api/v1/changes` | 实时推送 + 增量拉取 |
| WebDAV | `/webdav/*`（PROPFIND/PUT/COPY/MOVE/LOCK 等） | 桌面挂载盘 |
| 任务 | `GET /api/v1/tasks/{id}` | 目录级异步任务进度查询 |

> 想"找一个接口在哪个文件实现"：`api.go` 用 `mux.Handle("METHOD /path", ...d.handleXxx...)` 写明，`handleXxx` 就是实现函数，一般在同目录的 `handlers_*.go` 里。

## 10. 几个关键设计，读代码前先有个概念

为了让非资深阅读者不至于一头雾水，先建立这四个心智模型：

1. **JWT 分端**：令牌分 `web`（后台）/`desktop`（桌面）等端点，**后台令牌不能操作桌面能力**，反之亦然。令牌里不写权限，权限永远服务端判定。
2. **TUS 断点续传 + 单一写路径**：所有上传（TUS 分片、WebDAV PUT、秒传）最终都汇到 `finalize` 这一个"定稿"入口，保证写文件只有一条路径，不会互相打架。
3. **同步双通道**：服务端通过 SSE 推"有变化"；客户端再通过 `/changes` 游标**拉取**具体改动。推送丢了也不怕，拉取是权威。游标用全局自增号对齐。
4. **内容寻址存储**：`storage` 按文件内容的哈希存放对象，同一内容只存一份（去重），文件名只是元数据。

## 11. 第三方依赖（go.mod）很精简

`slimming` 后依赖大幅缩减，目前核心依赖只有：

- **pgx**（PostgreSQL 驱动）、**goose**（迁移）
- **go-redis**（Redis 客户端）
- **golang-jwt/v5**（JWT）
- **miniredis**（仅测试用）、**yaml.v3**（配置）

没有消息队列、没有重型框架、没有多后端存储 SDK（本地磁盘是唯一后端）。这对排障很友好：栈上没有太多"看不完的依赖"。

## 13. 从哪儿读起（给第一次上手的人）

1. `cmd/netdisk/main.go` —— 看装配顺序（5 分钟理解全局）
2. `internal/api/api.go` —— 看全部路由（5 分钟知道系统有哪些接口）
3. `deploy/config/config.example.yaml` —— 看都有哪些配置旋钮
4. 挑一个你最关心的业务：文件上传就追 `finalize`，组织架构就追 `orgsvc`，同步就追 `syncfeed`/`syncsse`
5. 排一个真实问题：从 `obs` 日志 / 某个接口报错 → 回 `handlers_*.go` → `repo/*.go` 看 SQL

> 黄金原则：**遇到"这个是干什么的"就去读那个包文件顶部的注释**——本仓库每个包/函数都有大量中文设计注释，是一部"活文档"。
