## 1. 测试分层总览

| 层 | 干什么 | 谁跑 |
|---|---|---|
| 编译 / 静态检查 | 保证能编译、无可疑构造 | 开发 / CI，自动 |
| 单元 + 集成测试 | 逐函数 / 逐接口验证业务规则 | 开发 / CI，自动 |
| 架构纪律门禁 | 保证分层、红线、文档一致性 | CI，自动 |
| 覆盖率门禁 | 保证关键包不被裸奔 | CI，自动 |
| 端到端探针 | 真实 HTTP 全链路冒烟 | 部署后 / 发布前，需真机 |
| 性能基线 | 验证列表 / 同步 / 并发吞吐达标 | 真机，可重复脚本 |
| 人工验收 | UI 点击、超长路径、真机平台等 | 运维 / 验收人员 |

> 项目里 `cmd/testsgate`、`cmd/depsguard`、`cmd/coveragegate` 都是**独立的门禁程序**。
> 本机命令与 CI 命令是同一条（CI 也接同样的命令）。

## 2. 自动化门禁（一条命令一层）

在仓库根目录（`Server-com/`）执行：

| 层 | 命令 | 拦住什么 |
|---|---|---|
| 编译 / 静态 | `go build ./... && go vet ./...` | 编译错误、可疑构造 |
| 单元 + 集成 | `NETDISK_TEST_DSN='...' go test ./... -count=1` | 全部 Go 用例（含真实 PG/Redis） |
| 集成没被跳过 | `go run ./cmd/testsgate` | "缺 DSN 整组 skip 而 CI 全绿"这类**假绿**，点名任何被跳过的用例 |
| 数据竞争 | `go run ./cmd/testsgate -race` | 数据竞争（需要 gcc） |
| 架构与文档纪律 | `go run ./cmd/depsguard` | 内核包依赖 HTTP 层 / 桌面纪律 / 红线 / 文档与运维制品一致性 |
| 覆盖率 | `go run ./cmd/coveragegate -profile <cover.out> -min 55` | 关键包覆盖率跌破阈值 |
| 端到端探针 | `go run ./cmd/probesmoke -pass <口令>` | 真实 HTTP 全链路（上传/下载/分享/WebDAV/审计/巡检…） |

> 集成测试需要 `netdisk_test` 库 + Redis。没有真实 PG/Redis 时集成用例会被跳过；
> `testsgate` 的作用就是**盯住"有没有用例被偷偷跳过"**，避免 CI 出现假绿。

## 3. 单元 + 集成测试（现状）

- 全量用例 **1042 个通过**，覆盖 39 个包 / **0 个被跳过**（`testsgate` 点名复核）。
- 覆盖分域：认证令牌 / 上传定稿 / 对象锁并发 / 目录语义 / 同步变更 / 分享 / 配额对账 / 巡检 / WebDAV。

**性能敏感断言的分层判据**（如并发定稿锁窗口 P95）：
- 主判据用**中位**（回归会让每一次持锁都变慢）；
- 尾部用 P95 < 500ms（吸收"全包并行 + 共用测试库"的机器抖动）。
- 反例验证：在锁临界区里人为 sleep → 中位立刻变慢、用例变红，说明是"临界区变宽"而非"抖动"。

## 4. 端到端探针（probesmoke）

一条命令对**运行中的真实服务**做全链路冒烟（51+ 步）：登录 → 目录 → 上传（TUS/WebDAV/multipart）→
下载/Range → 分享 → 同步事件 → 审计 → 巡检。

```sh
go run ./cmd/probesmoke -base http://127.0.0.1:8080 -user admin -pass '<口令>'
```

> 走反代时 SSE 头会被 Nginx 消费（`X-Accel-Buffering`），所以**探针应直连应用**（51/51 全过）；
> 走反代时为 50/51，且该差异已解释（不是故障）。

## 5. 性能基线（2026-09-12 实测）

脚本：`deploy/verify/06-perf-baseline.sh`（自包含、可重复，数字由脚本实测输出）。机器：Debian 13，
6 vCPU / ~2GB RAM / 顺序写 2723.6 MB/s（本机基线）。

| 验收点 | 阈值 | 实测 | 结论 |
|---|---|---|---|
| 10 万行目录列表 | P95 ≤ 500ms | **P95 107.2 ms**（默认页 limit=200） | 通过（余量约 4.7 倍） |
| 远端变更感知（`/changes` 可见） | P95 ≤ 3s | **P95 78.1 ms**（multipart 写） | 通过（余量约 37 倍） |
| 远端变更感知（SSE 帧到达） | P95 ≤ 3s | **P95 80.5 ms** | 通过 |
| 并发上传 8×8MiB | — | **9.66 MB/s**，成功 8/8，失败 0 | 通过 |
| 并发上传 16×8MiB | — | **10.57 MB/s**，成功 16/16，失败 0 | 通过（12 次被限速后重试） |
| 并发下载 8/16×8MiB | — | **1944 / 2580 MB/s** | 通过（页缓存命中，不能当磁盘吞吐） |

> **如实说明**：16 并发上传时 `POST /tus` 有 12 次被服务端 **429 限速**（`rate_limits.upload=10/s`），
> 脚本按退避重试后全部成功——这是**限速按设计生效**，不是上传失败。若验收要求"16 并发一次全过"，
> 需调大 `rate_limits.upload` 或降并发。下载 2GB/s 量级是"内存 + 虚拟盘"速度，只说明下载路径并发下无排队无错误。

### 复现方式

```sh
BASE=http://127.0.0.1:8080 USER=admin PASS='<口令>' \
ROWS=100000 NREP=60 NFEED=30 SAR="8 16" UPFILE=8388608 \
sudo sh deploy/verify/06-perf-baseline.sh | tail -n +1
```

脚本末尾打印（逐次样本 / 直方图 / 分位数 / verdict 判定行）。
默认自动清理探测数据；`KEEP=1` 可保留（排障用）。

| 验收域 | 复跑入口 |

## 7. 仍需人工执行的项（不要在自动化里假装覆盖）

| 项 | 为什么自动化盖不住 | 登记处 |
|---|---|---|
| Windows 超长路径现场 | 需要真实盘符与 `longPathAware` 生效环境 | 客户端验收清单 |
| 杀毒软件锁文件的重试行为 | 需要真实 AV 挂钩 | 同上（如实标注"未验证"） |
| 界面点击（登录/托盘/设置/冲突/远端浏览/检查更新） | 无 UI 自动化 | 客户端验收清单 |
| 24h 客户端长跑 | 时长与真实交互会话 | 发布前人工执行 |
| 第三方照手册演练（备份/恢复） | 需要"另一个人"按手册操作 | 演练台账 |

## 8. 三条测试纪律

1. **不能判定 ≠ 通过**：检查器遇到"无法判定"必须判失败，不能被当成通过。
2. **反向验证是断言的一部分**：每条关键断言都要做一次"把代码改坏 → 断言必须变红"，
   否则你不知道自己在盯什么（仓内已多次出现"改坏了照样绿"）。
3. **证据要能复跑**：证据 = 命令 + 真实输出 + 当时的版本；贴一段没有命令来源的输出不算证据。
