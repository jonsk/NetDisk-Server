## 1. Обзор и назначение

`Server-com` — это **серверная часть корпоративного сетевого диска**, написанная на **Go** и в конечном итоге компилируемая в **один исполняемый файл** (единый бинарный файл).
Он предоставляет общие командные пространства, мультипротокольную загрузку (TUS / WebDAV / multipart), версионированное финализирование, восприятие реального времени и синхронизацию,
детальные права доступа и управление квотами; его можно развёртывать как частный сетевой диск, так и использовать как файловый узел предприятия.

Сообщественная редакция (Server-com) сохраняет только **вход по паролю + панель администратора** и является функциональным подмножеством коммерческой редакции (Server-Ent).

**Ключевая идея: весь сервис — это «большой ящик», а снаружи с ним взаимодействуют четыре компонента.**

## 2. Общая архитектура

### 2.1 Состав развёртывания (четыре компонента)

| Компонент | Назначение | Примечание |
|---|---|---|
| **netdisk** (продукт этого репозитория) | Принимает HTTP-запросы, обрабатывает бизнес-логику, читает и пишет метаданные и объекты | Один и тот же бинарный файл обслуживает REST / WebDAV / TUS / SSE / встроенную панель администратора |
| **PostgreSQL 17 (минимально поддерживаемая)** | Единственный движок метаданных (все «элементы каталога/пользователи/пространства/квоты» находятся здесь) | Включает WAL-архивирование для восстановления на момент времени. **Минимум 17**: значение по умолчанию первичного ключа использует `gen_random_uuid()` (встроено с PG 13), поэтому нижняя граница не определяется UUID; минимум 17 (выровнено по версиям массовых дистрибутивов). Требования к версии см. в «Установка и развёртывание» (05-INSTALL.md) §1 |
| **Redis** | Сессии (token) / окна ограничения скорости / курсоры потока изменений / очередь задач | **Это не кэш**, при потере token все будут выведены из системы |
| **Nginx** | Обратный прокси, единый внешний порт | Нужен только в продакшене; в разработке можно обращаться к приложению напрямую |

                       │   └──────────────────────────────┘   │
                       └───────────┬──────────────────────────┘
                                   │
                     ┌─────────────┼─────────────┐
                     ▼             ▼             ▼
               ┌──────────┐  ┌────────┐   ┌────────────┐
               │PostgreSQL│  │ Redis  │   │Nginx(прокси)│

### 2.2 Почему единый бинарник + встроенный фронтенд

Фронтенд панели администратора после сборки в репозитории web **встраивается на этапе компиляции** в Go-бинарник (`internal/webui/dist/`),
и Go отдаёт его напрямую через `embed` (`/admin`). Преимущество: для распространения достаточно одного файла, не нужно отдельно развёртывать статический фронтенд-сайт на сервере.

> ⚠️ Поэтому **при изменении фронтенда необходимо перекомпилировать Go-бинарник**: сначала `pnpm build`, затем `go build`,
> при обратном порядке будет встроен старый результат сборки (скомпилируется, но страницы будут старыми и без ошибок).

## 3. Послойная архитектура (разделение пакетов internal)

Код разделён по ответственности на 5 уровней; верхний уровень может зависеть только от нижнего (механически проверяется `depsguard`):

```
┌─────────────────────────────────────────────────────────────┐
│ 4. Слой входа   cmd/  (netdisk / migrate / passwd / depsguard …)  │
├─────────────────────────────────────────────────────────────┤
│ 3. Слой интерфейса   internal/api/  (HTTP-обработчик, маршрутизация, middleware)          │
│            internal/webdavfs/ webdavauth/                     │
├─────────────────────────────────────────────────────────────┤
│ 2. Бизнес-слой   usersvc/orgsvc/spacesvc/filesvc/sharesvc/ │
│            uploadsvc/finalize/lifecycle/syncfeed/syncsse/    │
│            patrol/quotareconcile/consistency/credentials/    │
├─────────────────────────────────────────────────────────────┤
│ 1. Домен/данные  repo/(доступ к данным) model/(доменные модели) objlock/ storage/  │
│            authsvc/ cache/ auth/ apierr/reqctx/middleware/    │
├─────────────────────────────────────────────────────────────┤
│ 0. Фундамент      config/ db/ migrate/ ratelimit/ namepolicy/      │
│            dirops/ fastupload/ condreq/ webui/ obs/ syncssem  │
└─────────────────────────────────────────────────────────────┘
```

**Дисциплина (суть красных линий R-xx)**: пакеты «ядра» вроде `objlock` (блокировка), `storage` (объектное хранилище), `model` (доменные модели)
**ни в коем случае не должны зависеть от `internal/api` (HTTP-слой)**. Бизнес-логика должна быть развязана с HTTP,
чтобы при смене способа доступа (WebDAV/TUS/внутренний вызов) бизнес-правила не менялись.

## 4. Ключевые механизмы проектирования

### 4.1 finalize — единственный путь записи

Все загрузки (TUS-фрагменты, WebDAV PUT, прямая multipart-загрузка) в конечном итоге **сходятся в одну и ту же логику финализирования** `finalizeUpload()`:
1. Сначала проверяется мгновенная загрузка (если хэш содержимого уже существует — переиспользуется напрямую, защита от «отравления»);
2. Содержимое записывается в область объектов и получается **адресуемый по содержимому** объект;
3. В короткой транзакции записываются элемент каталога и счётчик ссылок;
4. Записывается поток изменений (sync_feed) для активации восприятия синхронизации.

Преимущество: поведение всех трёх каналов загрузки полностью идентично, исключаются уязвимости вида «один канал обходит какое-то правило».

### 4.2 Объектное хранилище с адресацией по содержимому

Объекты хранятся по **хэшу содержимого**, путь имеет вид `objects/xx/xx/<sha256>`:
- **Одно и то же содержимое хранится в одном экземпляре** (естественная дедупликация): если два пользователя загрузят один и тот же файл, на диске будет только одна копия;
- Имя файла отделено от содержимого: при переименовании данные не копируются, меняются метаданные;
- Незменяемый объект: после финализирования содержимое больше не перезаписывается, исключается «тихое перезатирание/дрейф файла».

### 4.3 Двухуровневая объектная блокировка (ADR-2)

Для предотвращения повреждения данных при одновременном финализировании/удалении одного и того же объекта несколькими запросами введена объектная блокировка:

| Уровень | Назначение | Способ удержания блокировки |
|---|---|---|
| **Блокировка уровня сессии** | Полный процесс финализирования, worker жизненного цикла (реальный путь записи) | Единое выделенное соединение с БД на всю длительность, удержание блокировки имеет верхний предел (потолок), чтобы избежать слишком длинной критической секции |
| **Блокировка уровня транзакции** | Чистое увеличение ссылки (+1) (копирование, шаринг в пространство) | Удерживается только в рамках одной короткой транзакции |

Ключ блокировки определяется хэшем объекта, порядок захвата — по возрастанию хэша, чтобы избежать взаимных блокировок.

### 4.4 Двухрежимная синхронизация (SSE + курсор)

Клиентам рабочего стола нужно «узнать сразу, как только на удалённой стороне что-то изменилось»:
- **SSE-рассылка** (`/sync/events`): в реальном времени отправляет изменения подключённым клиентам (быстро, но возможна потеря кадров);
- **Получение по курсору** (`/changes`): клиент с курсором (`since`) получает инкрементально (надёжно, как запасной вариант).

Оба используют **одну и ту же глобальную `change_seq`** (таблица `sync_feed`, глобально возрастающий порядковый номер),
клиент может чередовать их и дозапрашивать по `/changes` как по эталону. Так отпадает необходимость в периодических полных сканированиях, и изменения не теряются.

### 4.5 Раздельная аутентификация JWT по клиентам

После успешного входа выпускается JWT (HS256), раздельно для двух клиентов:
- Токены **web-клиента** (панель администратора) и **desktop-клиента** (клиент рабочего стола) независимы (R-14),
  чтобы утечка в одном месте не затронула всё;
- Токен доступа и токен обновления хранятся в Redis, поддерживается отзыв и «одиночное обновление» (в один момент времени успешен только один запрос обновления).

Сообщественная редакция сохраняет только **вход по логину и паролю** (`/api/v1/auth/login`).

### 4.6 Семантика каталогов и ограничения именования

- Глубина каталога ≤ 31 уровня и суммарный путь одного элемента ≤ 240 байт (двойной предел, настраивается);
- Проверка дубликатов имён без учёта регистра (`lower(name)` + уникальный индекс);
- Операции уровня каталога «перемещение/удаление поддерева», превышающие порог (по умолчанию 1000 строк), переводятся в **асинхронную задачу**, возвращается `task_id` для опроса клиентом.

## 5. Модель данных (ключевые таблицы)

| Таблица | Значение |
|---|---|
| `users` | Пользователи (хэш логина и пароля, email, отображаемое имя, роль) |
| `organizations` / `departments` / `groups` | Организация / отдел / группа |
| `spaces` | Пространства (личное пространство + командное пространство; включает квоту `used_bytes`, `last_seq`) |
| `space_members` | Участники пространства и права доступа |
| `files` | Элементы каталога (файлы и каталоги; `is_dir`, `parent_id`, `name`, `depth`, `size`) |
| `file_objects` | Объекты с адресацией по содержимому (хэш, четыре состояния: live/pending_delete…, счётчик ссылок `ref_count`) |
| `sync_feed` | Поток изменений (глобальный `change_seq`, хранение 90 дней) |
| `shares` | Ссылки общего доступа (token, права, срок действия) |
| `audit_logs` | Журнал аудита (в настоящее время зарезервированная заглушка, не сохраняется в сообщественной редакции) |

## 6. Проектирование конфигурации

- **Значения по умолчанию только в одном месте**: в структуре Go `internal/config.Default()`; удаление секции конфигурации не даёт нулевых значений, а возвращается к умолчанию;
- **secret никогда не попадает в yaml**: `JWT_SECRET`, пароль БД, пароль Redis передаются только через **переменные окружения** (`NETDISK_*`);
- Приоритет: Go-умолчание < файл конфигурации < переменные окружения;
- Самопроверка при запуске (`netdisk -config ... -check`): любые недопустимые элементы выводятся **все сразу** и завершается с ненулевым кодом, а не ждут первого запроса с ошибкой 500;
- Длительности задаются в читаемом виде (`5m`/`30s`/`24h`).

## 7. Ключевые процессы

### 7.1 Жизненный цикл одной загрузки (TUS)

```
Клиент ─PATCH фрагмент→ временная зона(tus-tmp) ─после передачи всего→ finalizeUpload()
    finalize: вычисление хэша → проверка мгновенной дедупликации → запись в область объектов(objects/) → короткая транзакция записи files+file_objects
             → запись sync_feed(change_seq++) → отправка SSE → возврат X-File-Id завершён
```

### 7.2 Цепочка обработки одного запроса

```
Nginx ─→ цепочка middleware(лог/восстановление/лимит/аутентификация) ─→ маршрутизация(ServeMux) ─→ handler ─→ бизнес-сервис ─→ repo(DBA)
```

## 8. Обзор точек входа интерфейса

| Точка входа | Описание |
|---|---|
| `REST /api/v1/*` | Аутентификация, пользователи, отделы, пространства, файлы, каталоги, загрузка, скачивание, общий доступ, события изменений |
| `Скачивание и Range` | Потоковое скачивание, байтовый Range / условные запросы (If-Match и т.д.) |
| `TUS /uploads/*` | Докачка фрагментов, повторное использование ticket, сбор временных файлов, уровень диска (>90% → 507) |
| `WebDAV /dav/*` | Стандартный WebDAV + PUT через финализирование (≤100МБ) |
| `SSE /sync/events` | Отправка изменений в реальном времени |
| `курсор /changes` | Инкрементальное получение по курсору |
| `GET /metrics` | Метрики мониторинга Prometheus (по умолчанию только loopback/доверенный прокси) |
| `GET /healthz` | Проверка работоспособности |
| `/admin/*` | Встроенная панель администратора (Go embed) |

## 9. Красные линии архитектуры (выдержка)

- Ядро-пакеты не должны зависеть от HTTP/API-слоя (семейство R-01);
- Глобальный порядок захвата блокировок фиксирован: строка spaces → строка files → file_objects (advisory + блокировка строк, по возрастанию хэша);
- OAuth / ключи всегда идут в переменные окружения, не попадают в репозиторий;
- Обход (patrol) **только для чтения**: ни в коем случае не исправляет автоматически, чтобы ложное срабатывание не превратилось в повреждение данных;
- Сверка квот, обход объектов, очистка потока изменений — все являются управляемыми фоновыми задачами, без неограниченного расширения.

## 10. Технологический стек

| Слой | Выбор |
|---|---|
| Язык | Go 1.26 |
| HTTP | стандартная библиотека `net/http` + цепочка middleware `ServeMux` |
| DB | pgx v5 + sqlc + миграции goose (только PostgreSQL) |
| Аутентификация | golang-jwt v5 (HS256) |
| Хранилище | локальное дисковое объектное хранилище (адресация по содержимому, пакет `storage` расширяем на несколько бэкендов) |
| Конфигурация | yaml.v3 + строгая проверка переменных окружения |
| Развёртывание | systemd + Nginx + Prometheus (единый порт, четыре компонента, без контейнеров) |
