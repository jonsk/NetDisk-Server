# Server-com: резервное копирование и восстановление

> Главная цель в одной фразе: **в любой момент времени можно восстановить «базу данных + объекты» до одной и той же точки во времени**.
> Сопутствующие скрипты находятся в `deploy/backup/`, автоматически запускаются systemd-таймерами.

---

## 1. Цели и стратегия резервного копирования

В сетевом диске есть два типа данных, которые **должны восстанавливаться вместе до одной и той же точки во времени**:

1. **Метаданные** (пользователи/пространства/элементы каталога/квоты… в PostgreSQL);
2. **Файлы объектов** (реальное содержимое, хранящееся на локальном диске по хэшу содержимого).

Резервное копирование только одного из них без другого приведёт к некорректному состоянию «файл есть, но база указывает на другой объект» или «файл целиком нулевых байтов».

| Данные | Способ | Частота | Хранение |
|---|---|---|---|
| PostgreSQL | `pg_dump -Fc` (ежедневная полная копия БД) + **WAL-архивирование** (реализует восстановление на момент времени) | Полная БД ежедневно в 02:30; WAL в реальном времени | dump 14 дней |
| Каталог объектов `/opt/netdisk/data` | borg (дедуплицированный инкрементальный) | **каждые 4 часа** | 7 дней / 4 недели / 6 месяцев |
| Redis (AOF) | Заходит в резервную копию вместе с каталогом объектов | как выше | как выше |

Два таймера запускаются автоматически (оба управляются `deploy/backup/netdisk-backup.sh`):

```sh
netdisk-backup.sh full      # Ежедневно: самопроверка WAL + инкремент объектов + полная PG + проверка чтения + очистка хранения
netdisk-backup.sh objects   # Каждые 4 часа: только инкремент каталога объектов
```

### Три «антиотказных» решения в реализации резервного копирования

1. **Проверка чтения сразу после резервного копирования**: если `pg_restore --list <dump>` не открывается — считается сбоем; резервная копия, которую только записали, но не проверили, — это лишь файл, «который вы считаете существующим».
2. **WAL-архивирование смотрит на «новые сбои», а не на «равно ли нулю»**: `failed_count` — накопительное значение, никогда не сбрасывается. Проверка «равно ли 0» превратила бы одну историческую ошибку в «резервное копирование с этого момента всегда падает». Теперь изменено на запись базовой линии и оповещение только по **инкременту**.
3. **Атомарная запись состояния JSON** (временный файл + `mv`): чтобы Prometheus не считывал наполовину записанный файл. «Состояние резервного копирования неизвестно» и «резервное копирование не выполнено» — это две совершенно разные аварийные ситуации.

## 2. Действительно ли резервное копирование можно восстановить? — Тренировка восстановления

> Резервное копирование ≠ возможность восстановления. Настоящая проверка — это **тренировка восстановления**: раз в квартал, `deploy/backup/netdisk-restore-drill.sh`.

Тренировка выполняет четыре действия, **сбой любого из них считается сбоем тренировки**:

1. Восстановление последней резервной копии **в отдельную временную БД** (`netdisk_drill_<дата>`, **ни в коем случае не трогать продакшен-БД**);
2. **Сравнение количества строк ключевых таблиц** продакшен vs восстановленная БД (users/spaces/files/file_objects/space_members/sync_feed/audit_logs);
3. **Воспроизведение каталога объектов**: восстановление из резервной копии во временный каталог, побайтовое сравнение хэша содержимого (sha256) для живых объектов;
4. Запись момента тренировки, оповещение при отсутствии тренировки более **90 дней**.

```sh
sudo /opt/netdisk/bin/netdisk-restore-drill.sh     # Записывается в /var/backups/netdisk/logs/drill-<дата>.log
```

> Необходимо оставить хотя бы один живой объект, иначе тренировка сможет проверить только «архив распаковывается», но не «содержимое воспроизводится» (восстановленный файл нулевых байтов всё равно «существует»). Можно создать его прямой передачей через WebDAV:
> `curl -u admin:<пароль> -T <локальный файл> http://127.0.0.1:8080/webdav/<space_id>/<имя файла>` (путь **должен содержать space_id**).

## 3. Восстановление на момент времени (PITR): восстановление до определённого момента

> Предпосылка: `archive_mode=on` + `archive_command` работают нормально (настроено при установке), и **имеется базовая физическая резервная копия** в качестве отправной точки.

```sh
# ① Получить базовую резервную копию (физическая копия, в сочетании с WAL позволяет «вернуться в прошлое»)
su - postgres -c "/usr/lib/postgresql/17/bin/pg_basebackup -D /var/backups/netdisk/base -Ft -z -X fetch"

# ② Восстановить в «каталог независимого экземпляра» (не перезаписывать продакшен-данные)
install -d -o postgres -g postgres -m 0700 /var/lib/postgresql/17/restore
tar -xzf /var/backups/netdisk/base/base.tar.gz -C /var/lib/postgresql/17/restore

# ③ Записать цель восстановления (восстановление до момента 2026-09-12 19:53)
cat >> /var/lib/postgresql/17/restore/postgresql.auto.conf <<'EOF'
restore_command = 'cp /var/lib/postgresql/wal_archive/%f %p'
recovery_target_time = '2026-09-12 19:53:00+08'
recovery_target_action = 'promote'
EOF
touch /var/lib/postgresql/17/restore/recovery.signal
chown -R postgres:postgres /var/lib/postgresql/17/restore

# ④ Запустить экземпляр восстановления на другом порту (сосуществует с продакшеном, не трогает продакшен)
su - postgres -c "/usr/lib/postgresql/17/bin/pg_ctl -D /var/lib/postgresql/17/restore \
  -o '-p 5433' -l /tmp/pitr.log start"
su - postgres -c "psql -p 5433 -Atc 'SELECT count(*) FROM files' netdisk"
```

Скрипт тренировки PITR (`netdisk-pitr-drill.sh`) автоматизирует этот процесс и действительно «совершает путешествие во времени»; критерий — не «база поднимается», а **данных после целевого момента не должно быть**: вставить `before`(T0) → взять физическую копию → записать целевой момент T → вставить `after`(T1>T) → восстановить из копии до T → утверждение: в БД `before` существует, `after` **не существует**.

Практические моменты:
- Для базовой копии используйте формат **plain** (`-Fp`, сразу раскладывается в готовый каталог данных) — это проще, чем `-Ft` (сжатая упаковка);
- Параметры экземпляра восстановления вроде `max_connections` **должны быть ≥ главной БД**, иначе PG просто откажет в восстановлении;
- Тренировку нужно проводить на **реплике**: после promote этот каталог уже был записан и перестаёт быть «копией того момента»; базовая копия — это артефакт, тренировка может трогать только её копию.

## 4. Воспроизведение файлов объектов (выполняется отдельно)

```sh
export BORG_REPO=/var/backups/netdisk/borg BORG_PASSPHRASE=$(cat /etc/netdisk/borg.passphrase)
borg list --last 3 "$BORG_REPO"                  # Посмотреть последние несколько копий
cd /tmp/restore && borg extract "$BORG_REPO::full-2026-09-12T19:53:38"
# Восстановленные файлы имеют вид /tmp/restore/opt/netdisk/data/objects/xx/yy/<sha256>
```

> **Объекты и база данных должны быть из одного и того же момента времени**: воспроизвести только объекты без базы = «файл есть, но база указывает на другой объект»; воспроизвести только базу без объектов = «файл целиком нулевых байтов». Скрипт тренировки связывает оба вместе именно для предотвращения этого.

## 5. AOF в Redis

В Redis хранятся состояние входа и курсоры (**это не кэш**; «три жёстких требования» к обязательному включению постоянства см. в «Установка и развёртывание» (05-INSTALL.md) §5). Ключевой момент этого раздела — включить в резервное копирование также и AOF:

```sh
redis-cli -a <пароль> --no-auth-warning BGREWRITEAOF      # Вручную запустить перезапись AOF
ls -l /var/lib/redis/appendonlydir/                     # Здесь располагаются AOF и manifest
```

Способ резервного копирования: вместе с каталогом объектов заходит в borg, либо после ежедневного `BGREWRITEAOF` отдельно `cp`. **Потеря AOF → все пользователи заново входят в систему** (данные не теряются).

## 6. Соответствующие оповещения

Тесно связанные с резервным копированием/восстановлением оповещения (правила см. в `deploy/prometheus/netdisk-alerts.yml`, критерии по метрикам подробно см. в «Эксплуатация» (06-OPS.md) §4):

- `NetdiskBackupStale` / `NetdiskObjectsBackupStale`: полная БД/объекты не были успешно скопированы дольше ожидаемой частоты;
- `NetdiskWalArchiveFailing`: WAL-архивирование постоянно падает, `pg_wal` заполнит диск;
- `NetdiskRestoreDrillOverdue`: с момента последней тренировки прошло > 90 дней, пора проводить тренировку восстановления.

## 7. Пока не сделано (честно отмечено)

- **Еженедельная базовая физическая резервная копия** ( «отправная точка» PITR). В настоящее время `netdisk-backup.sh` выполняет только `pg_dump` (логическое резервное копирование) и не выдаёт физическую базовую копию — поэтому область «возврата в прошлое» ограничена той базовой копией, которая осталась после ручной тренировки. Рекомендуется до ввода в эксплуатацию добавить **еженедельный таймер `pg_basebackup`** (хранение 4 копий).
- **Удалённые реплики**. В настоящее время все реплики резервных копий находятся на одном и том же диске, **поломка диска = данные и резервная копия пропадают вместе**, это самая большая точка отказа текущего решения. Рекомендуется добавить удалённый репозиторий borg или реплику объектного хранилища, чтобы синхронизировать резервную копию за пределы локальной машины.
