# Руководство по чтению кода Server-com

> Применимая версия: Server-com (открытая версия / Community) · однобинарный сетевой диск на Go серверной стороны
> Для кого: инженеров и операторов, которым нужно понять, отладить или доработать этот код.
> Это руководство рассказывает «как организован код, как текут данные, где искать для изменения X», без пояснения алгоритмов построчно.
> Постепенное принятие по модулям и красные линии разработки см. в `01-功能清单.md` в этом же каталоге; авторитетный дизайн см. в `D:\WorkSpace\GO\Doc\网盘系统架构设计文档.md` (V3.0).

## 1. Что такое этот репозиторий

`Server-com` — это **бэкенд-сервис** корпоративного сетевого диска, написанный на Go, в итоге компилируемый в **один исполняемый файл** (один бинарник).

Он предоставляет извне четыре типа возможностей:

| Возможность | Описание | Основной вход |
|---|---|---|
| REST управление/файловый интерфейс | панель управления, CRUD файлов, скачивание,分享 | `/api/v1/*` |
| TUS возобновляемая загрузка | загрузка больших файлов фрагментами | `/tus/*` |
| WebDAV | десктопное монтируемое устройство (совместимость с файловым протоколом) | `/webdav/*` |
| SSE синхронизация реального времени | push «файл изменился» клиенту, затем клиент выбирает инкрементально | `/api/v1/events` |

Он **не** отвечает за: HTTP обратное прокси (Nginx), фронтенд-страницы (репозиторий `web`), десктоп-клиент (репозиторий `desktop`). Это три — независимые репозитории или внешние компоненты.

> Одной фразой: этот репозиторий = куча Go-пакетов + набор команд + скрипты миграции + материалы развёртывания, в итоге производящий бинарник `netdisk`.

## 3. Команды (cmd/) — каждая это отдельная маленькая программа

В `cmd/` 8 каталогов, каждый — отдельная программа `main`:

| Команда | Что делает | Когда использовать |
|---|---|---|
| **netdisk** | **главный сервис**, единственный процесс для продакшена | тот, который запускает `systemd` |
| **migrate** | миграция БД | при развёртывании `go run ./cmd/migrate up` |
| **passwd** | эксплуатация учётных записей: создание / сброс пароля / вкл-выкл | ручная операция с аккаунтом |
| **probesmoke** | end-to-end зонд: реальный HTTP прогон вход→загрузка→скачивание | самотестирование в период разработки |
| **devdb** | обслуживание локальной БД разработки/тестов | локально разработчиком |
| **depsguard** | шлюз архитектуры: проверка «ядро-пакеты не должны зависеть от HTTP-слоя» и т.д. | статическая проверка CI |
| **testsgate** | шлюз интеграционных тестов: подтверждение что тесты реально прошли | CI |
| **coveragegate** | шлюз покрытия: подсчёт покрытия операторов по пакетам | CI |

В продакшене важны только первые два: `netdisk` и используемый при развёртывании `migrate`. Остальные — вспомогательные для разработки/CI.

## 4. Карта пакетов internal/ — где код и что делает

36 пакетов по обязанностям делятся на пять слоёв. Понимание слоёв — ключ к чтению репозитория: **HTTP-слой только «принимает запрос, вызывает сервис, возвращает ответ», бизнес-логика в сервис-слое, реальное чтение/запись БД в repo-слое, самый нижний — БД/Redis/диск.**

### 4.1 Вход и HTTP-слой (первое, с чем вы столкнётесь в этом репозитории)

| Пакет | Обязанность |
|---|---|
| **api** | **общая сборка маршрутов**. все сопоставления URL↔обработчик в `api.go`. Почти всё «какой интерфейс вызывает кого» можно найти здесь |
| **middleware** | цепочка middleware: requestID, реальный IP, структурированные ошибки, лог, восстановление после сбоя. «контрольно-пропускные пункты», через которые проходит запрос |
| **apierr** | единая обёртка ошибок (HTTP статус + бизнес-код + китайский текст) |
| **webui** | вход статических ресурсов фронта `/admin` (embed в бинарник, Nginx больше не обслуживает) |
| **reqctx** | инструмент помещения «текущего пользователя» (Actor) в контекст запроса |

### 4.2 Аутентификация и права

| Пакет | Обязанность |
|---|---|
| **auth** | выдача/проверка JWT (сам токен, stateless) |
| **authsvc** | бизнес-оркестрация входа по логину/паролю/обновления/выхода (запрос БД, проверка пароля, блокировка, связь версии token) |
| **webdavauth** | канал Basic-аутентификации WebDAV |
| **credentials** | Hash пароля (типа bcrypt) и политика сложности |

### 4.3 Сервис-слой бизнеса (каждый соответствует классу бизнеса, самый достойный детального чтения)

| Пакет | Обязанность |
|---|---|
| **usersvc** | управление пользователями панели (создание/вкл-выкл/роли) |
| **orgsvc** | организационная структура (дерево отделов) |
| **spacesvc** | пространства (личные/командные) и совместная работа участников |
| **filesvc** | метаданные файлов (список/переименование/перемещение/удаление/создание каталогов) |
| **uploadsvc** | создание задач загрузки, проверка ticket, TUS data plane |
| **fastupload** | челлендж «доказательство владения» для мгновенной загрузки |
| **finalize** | **финализирование** — единственный вход финальной записи всех загрузок, самый критичный путь записи во всей сети |
| **sharesvc** | ссылки для分享 (единственный выход системы без входа) |
| **dirops** | очередь асинхронных задач уровня каталогов (операции с огромными каталогами в фоне) |
| **quotareconcile** | сверка квот и оповещение о дрейфе |
| **patrol** | патруль объектов: сканирование диска на утечки/осиротевшие файлы |

### 4.4 Доменные модели и синхронизация

| Пакет | Обязанность |
|---|---|
| **model** | сущности (struct), строго соответствующие таблицам БД |
| **namepolicy** | единственный судья имён файлов (проверка легитимности, длины, глубины) |
| **objlock** | объектный уровень блокировки (взаимоисключение при записи одного файла, предотвращение конкурентной перезаписи) |
| **syncfeed** | запись/чтение потока изменений (кто что изменил) |
| **syncsse** | канал SSE событий (push клиентам) |

### 4.5 Инфраструктура (большую часть времени достаточно знать, что она существует)

| Пакет | Обязанность |
|---|---|
| **config** | загрузка конфигурации (yaml + переменные окружения) |
| **db** | пул соединений PostgreSQL и транзакции |
| **cache** | обёртка Redis и соглашение об именовании ключей |
| **ratelimit** | rate limit на основе Redis |
| **repo** | SQL-репозиторий — **весь SQL здесь**, это вход «посмотреть данные» |
| **storage** | объектное хранилище локального диска (content-addressed, файлы по Hash) |
| **migrate** | миграция версий БД (goose) |
| **obs** | структурированное логирование (slog) |
| **lifecycle** | конечный автомат жизненного цикла объектов |
| **condreq** | HTTP условные запросы (If-Match/If-None-Match, оптимистичная блокировка) |
| **webdavfs** | нижнеуровневое файловое представление для WebDAV |

> **Быстрая справка по чтению**: чтобы изменить «какой-то HTTP интерфейс» → ищите строку маршрута в `internal/api/api.go` + соответствующий `handlers_*.go`;
> чтобы узнать «как читать/писать БД» → ищите `internal/repo/`;
> чтобы найти «финальную запись загрузки на диск» → смотрите `internal/finalize/` (единственный путь записи).

## 5. Сборка запуска — как сервис «собирается»

Всё начинается с `cmd/netdisk/main.go`. По пронумерованным шагам в комментариях, порядок сборки таков:

1. **Конфигурация**: значения по умолчанию ← yaml ← переменные окружения (позже перекрывает ранее)
2. **Проверка**: единовременный вывод всех проблем, при наличии проблем — отказ запуска (fail-fast)
3. **PostgreSQL**: подключение к БД, запуск миграций
4. **Redis**: при невозможности подключения — отказ запуска (от него зависят аутентификация/rate limit)
5. **Управление токенами**: инициализация выдачи JWT, Redis, rate limiter, различных бизнес-сервисов
6. **HTTP сервис**: монтирование маршрутов из `internal/api` на порт, запуск прослушивания

Этот файл — место «внедрения зависимостей» — где и какие сервисы созданы через new, какие зависимости переданы, всё в этом одном файле. Чтобы понять «как собирается тот или иной сервис» — читайте его; чтобы добавить системе зависимость — тоже меняйте его.

## 6. Как проходит один запрос (поняв поток, поймёте репозиторий)

На примере «пользователь после входа запрашивает список файлов», цепочка такова:

```
        ┌────────────────────────────────────────────┐
        │  Nginx：HTTPS 终结、反代、来源 IP 透传       │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  middleware 中间件链（internal/middleware） │
        │  requestID → realIP → structuredErrors →   │
        │  logging → recoverer（崩溃兜底）            │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  api 路由（internal/api/api.go）            │
        │  鉴权(auth) → 限速(ratelimit) → handler    │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  handlers_*.go  解析参数、调用服务          │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  业务服务层（filesvc/uploadsvc/...）         │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
        │  repo 层：「唯一 SQL 的地方」→ PostgreSQL    │
        │  storage 层：读写磁盘对象                    │
        └────────────────────────────────────────────┘
```

**Запомните жирным шрифтом эту фразу**: Слой `api` отвечает за «внешний вид», слой `repo` отвечает за «общение с БД», промежуточный сервис-слой отвечает за «бизнес-правила». Чем яснее слои, тем при изменении в одном месте затрагивается только оно.

## 7. Как управлять конфигурацией

Смотрите `deploy/config/config.example.yaml` (пример конфигурации, самый авторитетный список полей), а также `internal/config/config.go` (логика загрузки).

- Приоритет источников конфигурации: **значения по умолчанию в коде < yaml файл < переменные окружения**.
- **Чувствительные элементы (пароли, ключи) передаются только через переменные окружения, никогда не в yaml**. Например `NETDISK_DB_PASSWORD`, `JWT_SECRET`, `NETDISK_REDIS_PASSWORD`.
- Крупные блоки конфигурации включают: `server` (порт/прокси), `database`, `redis`, `jwt` (срок действия токена), `policy` (квота/глубина/лимит размера), `patrol` (патруль), `webui` (префикс панели), `storage` (корневой каталог хранилища), `log`, `rate_limits` (rate limit).
- При запуске выполняется проверка; если какой-то rate limit равен 0, каталог хранилища недоступен для записи и т.д. — будет перехвачено.

> Совет оператору: изменить конфигурацию → отредактировать yaml или переменные окружения → перезапустить `netdisk`; **изменение фронтенда требует перекомпиляции Go-бинарника** (так как страницы embed внутрь), простого перезапуска процесса недостаточно.

## 9. Краткий обзор HTTP интерфейсов

Все маршруты сосредоточены в `internal/api/api.go`. Сгруппированы по функциям (детали аутентификации опущены):

| Группа | Пример пути | Описание |
|---|---|---|
| Здоровье / версия | `GET /healthz`, `GET /api/v1/version` | проверка живости, согласование версии (без входа) |
| Аутентификация | `POST /api/v1/auth/login` / `refresh` / `logout` | вход по логину/паролю и продление токена |
| Моя информация | `GET /api/v1/me` | текущий вошедший пользователь |
| Файлы | `GET /api/v1/files`, `GET /api/v1/files/{id}/content` | список, скачивание (поддержка Range) |
| Операции записи файлов | `PATCH /api/v1/files/{id}`, `DELETE /api/v1/files/{id}`, `POST /api/v1/files/dirs` | переименование, удаление, создание каталога |
| Загрузка | `POST /api/v1/upload/create`, `/tus/*` | создание задачи загрузки + TUS фрагментная загрузка |
| Мгновенная загрузка | `POST /api/v1/upload/{id}/finish` | финализирование мгновенной загрузки после прохождения доказательства владения |
| Блокировка редактирования | `POST/GET/DELETE /api/v1/files/{id}/lock` | блокировка совместного редактирования файлов |
| 分享 | `POST /api/v1/shares`, `GET /api/v1/shares/{token}/meta` | ссылки для分享 (скачивание без входа) |
| Пространства | `GET /api/v1/spaces`, `POST /api/v1/spaces` | мои пространства, создание пространства |
| Управление организацией/пользователями | `/api/v1/admin/departments*`, `/api/v1/admin/users*` | управление панелью (нужен администратор) |
| Синхронизация | `GET /api/v1/events` (SSE), `GET /api/v1/changes` | push в реальном времени + инкрементальная выборка |
| WebDAV | `/webdav/*` (PROPFIND/PUT/COPY/MOVE/LOCK и т.д.) | десктопное монтируемое устройство |
| Задачи | `GET /api/v1/tasks/{id}` | запрос прогресса асинхронной задачи уровня каталогов |

> Чтобы «найти, в каком файле реализован интерфейс»: в `api.go` записано `mux.Handle("METHOD /path", ...d.handleXxx...)`, `handleXxx` — это функция реализации, обычно в `handlers_*.go` того же каталога.

## 10. Несколько ключевых проектных решений, понятных до чтения кода

Чтобы менее опытный читатель не запутался, сначала создайте эти четыре ментальные модели:

1. **JWT по эндпоинтам**: токены разделены на эндпоинты `web` (панель) / `desktop` (десктоп) и т.д., **токен панели не может оперировать возможностями десктопа**, и наоборот. В токене не пишутся права, права всегда определяются сервером.
2. **TUS возобновляемая загрузка + единый путь записи**: все загрузки (TUS фрагменты, WebDAV PUT, мгновенная загрузка) в итоге сходятся в один вход «финализирования» `finalize`, гарантируя, что запись файла имеет только один путь, без конфликтов.
3. **Двойной канал синхронизации**: сервер через SSE push «есть изменение»; клиент затем через курсор `/changes` **выбирает** конкретные изменения. Если push потерян — не страшно, выборка авторитетна. Курсор выравнивается глобальным автоинкрементным номером.
4. **Content-addressed storage**: `storage` хранит объекты по Hash содержимого файла, одинаковое содержимое хранится в одном экземпляре (дедупликация), имя файла — лишь метаданные.

## 11. Сторонние зависимости (go.mod) очень лаконичны

После `slimming` зависимости значительно сокращены, сейчас ключевые зависимости только:

- **pgx** (драйвер PostgreSQL), **goose** (миграции)
- **go-redis** (клиент Redis)
- **golang-jwt/v5** (JWT)
- **miniredis** (только для тестов), **yaml.v3** (конфигурация)

Нет очереди сообщений, нет тяжёлых фреймворков, нет SDK многобэкенд хранилищ (локальный диск — единственный backend). Это дружественно к отладке: в стеке нет слишком много «необозримых зависимостей».

## 12. Краткая памятка по сборке / запуску / развёртыванию

```bash
# Локальная сборка (нужен Go 1.26+)
go build ./...            # компиляция всего (проверка на ошибки)
go vet ./...              # статическая проверка
go run ./cmd/depsguard    # шлюз архитектуры (также в CI)

# Реальный артефакт развёртывания (это делает deploy/build-release.sh)
```

## 13. С чего начать чтение (для впервые приступающих)

1. `cmd/netdisk/main.go` —— посмотрите порядок сборки (5 минут на понимание全局)
2. `internal/api/api.go` —— посмотрите все маршруты (5 минут, чтобы узнать, какие интерфейсы есть у системы)
3. `deploy/config/config.example.yaml` —— посмотрите, какие есть ручки конфигурации
4. Выберите самый важный для вас бизнес: загрузка файлов → преследуйте `finalize`, организационная структура → `orgsvc`, синхронизация → `syncfeed`/`syncsse`
5. Отладьте реальную проблему: от лога `obs` / ошибки какого-то интерфейса → к `handlers_*.go` → `repo/*.go` посмотрите SQL

> Золотое правило: когда встречаете «что это делает» — читайте комментарии в начале того файла пакета — в этом репозитории у каждого пакета/функции множество китайских проектных комментариев, это «живая документация».
