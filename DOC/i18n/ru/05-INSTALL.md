# Server-com: установка и развёртывание

> В этом документе описано только **развёртывание с нуля до готовности к эксплуатации**; текущее обслуживание / устранение неполадок — см. в «Эксплуатация» (06-OPS.md), защита данных — в «Резервное копирование» (07-BACKUP.md).
> Сопутствующие скрипты репозитория находятся в `deploy/`, для подавляющего большинства шагов есть готовые скрипты (идемпотентные, повторно запускаемые).
>
> **У каждого шага два варианта выполнения, выберите любой**: **① через скрипт** (готовые скрипты в `deploy/`, идемпотентные, рекомендуемые) —
> **② вручную командами** (полностью без скриптов, ввод команд по одной, удобно для аудита и проверки каждого этапа).
> Оба варианта дают одинаковый результат — выберите привычный, не нужно делать оба.

## 1. Форма развёртывания и предварительные требования

Вся сетевая папка — это **один Go-исполняемый файл** (`netdisk`), внешне ему помогают только четыре компонента:

```
Nginx(80/443) ─реверс-прокси─▶ netdisk(:8080) ─▶ PostgreSQL 17 (:5432)
                                      ─▶ Redis (:6379)
```

| Компонент | Требование по версии | Где устанавливается |
|---|---|---|
| netdisk | Артефакт сборки репозитория | Локально `/opt/netdisk/` |
| PostgreSQL | **минимум 17** (см. ниже) | Локально |
| Redis | 7+ | Локально |
| Nginx | рекомендуется 1.26+ | Локально (продакшен) |

> **Почему минимально поддерживается PostgreSQL 17?**
> Значение по умолчанию для первичного ключа использует `gen_random_uuid()` (см. скрипт миграции `00001_init.sql`) — это **встроенная в PG начиная с 13** функция генерации UUID, поэтому нижняя граница версии не связана с UUID. В этом проекте минимальная поддерживаемая версия зафиксирована на **PG 17** (в соответствии с версией, поставляемой современными популярными дистрибутивами), и документ по архитектуре ADR-1 также основан на этом. Если на месте используется 15/16, тоже будет работать (gen_random_uuid совместим), но стратегия архивации/долгосрочной поддержки ведётся по 17. Система сейчас поддерживает только эту СУБД (MySQL и прочие не подключаются).

## 2. Установка зависимостей

> На этом шаге устанавливаются: инструменты резервного копирования (borg/rsync), PostgreSQL 17, Redis, Nginx.
> Важный момент: **в системном репозитории Debian 13 уже есть PostgreSQL 17**, что точно соответствует минимальной поддерживаемой версии проекта — просто устанавливайте, **дополнительный источник PGDG не нужен** (если в системном репозитории на месте версия ниже, например в Debian 12 поставляется 15, тогда добавьте PGDG и установите 17 по ручным командам ниже).

```sh
# Поручаем скрипту: установить postgresql-17/redis/nginx/borg → отключить Apache, освободив 80/443
sudo bash deploy/provision/01-install-packages.sh
```

Скрипт выведет номер версии каждого компонента для подтверждения и в конце напечатает `INSTALL_DONE`.

> **Без скрипта, пошагово вручную** (эквивалентно `01-install-packages.sh`):

```sh
# ① Установить PostgreSQL 17 / Redis / Nginx / инструмент резервного копирования borg
#    (в Debian 13 уже есть PG17, устанавливаем напрямую; если версия в системном репозитории
#     слишком низкая, сначала добавьте источник PGDG, см. примечание ниже)
sudo apt-get update
sudo apt-get install -y postgresql-17 redis-server nginx borgbackup

# ② Отключить Apache, освободив 80/443 (только если Apache установлен на этом хосте)
sudo systemctl disable --now apache2 2>/dev/null || echo 'Apache отсутствует, пропускаем'
```

> Скрипт-версия объединяет эти 3 шага в одну команду `sudo bash deploy/provision/01-install-packages.sh`, дополнительно выполняя «печать номеров версий компонентов для подтверждения + вывод `INSTALL_DONE`».

> Подсказка: официальный источник PGDG в некоторых регионах медленный, можно использовать внутреннее зеркало
> (например, `https://mirror.nju.edu.cn/postgresql/repos/apt`).

## 3. Подготовка системы (что делает этот шаг)

> Цель: создать **учётную запись службы без права входа**, создать каталоги программы и правильно задать им «владельца», сгенерировать случайные пароли.

```sh
sudo bash deploy/provision/02-provision-base.sh
```

Конкретно он выполняет три действия (каждое можно проверить по результату `ls`):

1. **Создание учётной записи службы `netdisk`**: учётная запись только для запуска службы, без права входа
   (ей предоставляются минимальные права; программа только читает исполняемый файл, записывает в свой каталог данных).
2. **Создание каталогов и назначение владельца** (самое критичное — неверный владелец приведёт к немедленному отказу самопроверки при запуске службы):

   | Каталог | Владелец | Что содержится |
   |---|---|---|
   | `/opt/netdisk/data` | netdisk | Корень объектов и временных файлов (объекты по адресу содержимого, TUS-временная зона) |
   | `/etc/netdisk` | root:netdisk | Конфигурация + секреты |
   | `/var/log/netdisk` | netdisk | Журналы приложения |
   | `/var/lib/netdisk` | netdisk | JSON-статус резервного копирования/учений |

3. **Генерация файла случайных паролей `/etc/netdisk/secrets.env`**: однократно генерируются пароль БД, ключ JWT,
   пароль Redis и т. д. (**никогда не попадает в репозиторий и никогда не пишется в yaml**), используется последующими скриптами и программой.

> **Без скрипта, пошагово вручную** (соответствует трём действиям `02-provision-base.sh`):

```sh
# ① Создать учётную запись службы netdisk без права входа (системная учётная запись, без домашнего каталога, заблокированная оболочка)
sudo useradd --system --no-create-home --shell /usr/sbin/nologin netdisk

# ② Создать каталоги и назначить владельца (неверный владелец — самопроверка службы откажет)
sudo install -d -o netdisk -g netdisk -m 0750 /opt/netdisk/data    # корень объектов и временных файлов
sudo install -d -o root   -g netdisk -m 0750 /etc/netdisk          # конфигурация + секреты
sudo install -d -o netdisk -g netdisk -m 0750 /var/log/netdisk     # журналы приложения
sudo install -d -o netdisk -g netdisk -m 0750 /var/lib/netdisk     # статус резервного копирования/учений

# ③ Сгенерировать файл случайных паролей secrets.env (сначала получить случайную строку, затем записать, в конце сузить права)
DB_PASS=$(openssl rand -base64 24)
REDIS_PASS=$(openssl rand -base64 24)
JWT_SECRET=$(openssl rand -base64 48)
sudo tee /etc/netdisk/secrets.env >/dev/null <<EOF
NETDISK_DB_PASSWORD=$DB_PASS
NETDISK_REDIS_PASSWORD=$REDIS_PASS
NETDISK_JWT_SECRET=$JWT_SECRET
EOF
sudo chown root:netdisk /etc/netdisk/secrets.env
sudo chmod 0640 /etc/netdisk/secrets.env
```

> Имена полей сверяйте с переменными окружения, которые программа реально читает (см. `deploy/systemd/secrets.env.example`).
> Скрипт-версия объединяет эти 3 шага в одну команду `sudo bash deploy/provision/02-provision-base.sh`.
> Пароли генерируются один раз; для ротации измените этот файл и перезапустите службу.

## 4. Настройка PostgreSQL

> На этом шаге PG настраивается в состояние «подходящее для этого сервера + безопасное»: слушать только локально, адаптироваться под малый объём памяти,
> включить архивацию WAL (предпосылка точечного восстановления во времени), создать роль и базу данных, выделенные для программы.

```sh
sudo bash deploy/provision/03-provision-postgresql.sh
```

Назначение каждой настройки (всё записывается в `/etc/postgresql/17/main/conf.d/`):

| Настройка | Значение | Зачем |
|---|---|---|
| `listen_addresses` | `localhost` | Слушать только локально, порт PG **не появляется на сетевом интерфейсе** |
| `max_connections` | 100 | Со стороны приложения максимум 32 соединения, запас для обслуживания/psql |
| `shared_buffers` | 128MB | Адаптация под сервер с малым объёмом памяти (иначе по умолчанию под большую память съест всё) |
| `archive_mode=on` + `archive_command` | — | **Архивация WAL**: предпосылка точечного восстановления (PITR); `pg_wal` не заполнит диск |
| pg_hba | Только loopback | Отказать в прямом доступе из локальной сети, доступ только с локального хоста |

В конце он также:
- создаёт роль `netdisk` и базу данных `netdisk` (owner=netdisk);
- создаёт расширение `pg_trgm` (требуется скрипту создания таблиц; создано заранее суперпользователем, чтобы избежать различий в правах при миграции).

> **Без скрипта, пошагово вручную** (эквивалентно `03-provision-postgresql.sh`):

```sh
# ① Тюнинг + включение архивации WAL (запись в conf.d, чтобы не перезаписалось при следующем крупном обновлении версии)
sudo tee -a /etc/postgresql/17/main/conf.d/netdisk.conf >/dev/null <<'EOF'
listen_addresses = 'localhost'
max_connections = 100
shared_buffers = 128MB
archive_mode = on
archive_command = 'test ! -f /var/lib/postgresql/wal_archive/%f && cp %p /var/lib/postgresql/wal_archive/%f'
EOF
sudo install -d -o postgres -g postgres -m 0700 /var/lib/postgresql/wal_archive

# ② Создать роль и базу, выделенные для программы (пароль взять из secrets.env из §3)
sudo -u postgres psql <<'EOF'
CREATE ROLE netdisk LOGIN PASSWORD '<пароль БД>';
CREATE DATABASE netdisk OWNER netdisk ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C' TEMPLATE template0;
EOF

# ③ Создать расширение pg_trgm (внутри базы, суперпользователем, для использования при миграции)
sudo -u postgres psql -d netdisk -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

# ④ Перезапуск для применения (в Debian по умолчанию pg_hba уже разрешает только локальный доступ, доп. изменения не нужны)
sudo systemctl restart postgresql
```

> Если локаль в базе на месте не UTF-8, обязательно создайте базу способом из шага ② `TEMPLATE template0` + `LC_COLLATE 'C'`, чтобы гарантировать определённый порядок байтов, близкий к Linux-продакшену.
> Скрипт-версия объединяет эти 4 шага в одну команду `sudo bash deploy/provision/03-provision-postgresql.sh` (включая самопроверку версии/соединения).

## 5. Настройка Redis

> На этом шаге Redis настраивается так, чтобы «при перезапуске не терялась сессия входа и не происходило вытеснение пользователей».

```sh
sudo bash deploy/provision/04-provision-redis.sh
```

В Redis хранятся не обычные кэши, а **токены / окна ограничения скорости / курсоры синхронизации** — при их потере это равносильно «выходу всех пользователей из системы».
Поэтому есть **три жёстких требования**, нехватка любого вызовет проблемы:

| Требование | Значение | Что будет при нехватке |
|---|---|---|
| Установить пароль доступа | `requirepass <пароль>` | Полный отказ входа/ограничения скорости |
| Включить постоянство AOF | `appendonly yes` + `appendfsync everysec` | Один перезапуск = все пользователи выйдут из системы |
| Запретить вытеснение ключей | `maxmemory-policy noeviction` | Вытеснение ключей token/курсоров = случайный сброс пользователей в offline |

Скрипт также: привяжет прослушивание к локальному хосту (`bind 127.0.0.1`), после перезапуска проверит доступ по паролю (без аутентификации должно быть отказано, после аутентификации PING проходит).

> Верхний предел памяти 96MB — адаптация под сервер с малым объёмом памяти; при достижении предела, из-за `noeviction`, будет **ошибка**, а не тихая потеря ключей —
> ошибка позволяет выявить проблему, вытеснение лишь тихо сбрасывает людей в offline.

> **Без скрипта, пошагово вручную** (эквивалентно `04-provision-redis.sh`):

```sh
# Три жёстких требования + привязка к локальному хосту + малый предел памяти, добавляется в конфиг Redis Debian
sudo tee -a /etc/redis/redis.conf >/dev/null <<EOF
bind 127.0.0.1
requirepass <пароль Redis>
appendonly yes
appendfsync everysec
maxmemory-policy noeviction
maxmemory 96mb
EOF
sudo systemctl restart redis-server

# Проверка: без аутентификации должно быть отказано, после аутентификации PING проходит
redis-cli -a <пароль Redis> --no-auth-warning PING   # должен вернуть PONG
```

> Ни одно из трёх жёстких требований не должно отсутствовать (см. таблицу выше). Скрипт-версия `sudo bash deploy/provision/04-provision-redis.sh`
> дополнительно выполняет проверку по паролю после перезапуска (без аутентификации должно быть отказано).

## 6. Сборка и развёртывание netdisk

### 6.1 Сборка (порядок важен)

```sh
# Окружение (внутреннее ускорение + отключение проверки)
export GOPROXY=https://goproxy.cn,direct GOSUMDB=off
cd Server-com
# ⚠ Фронтенд админ-панели компилируется (embed) в бинарный файл на этапе сборки:
#   если меняли фронтенд, сначала pnpm build, затем go build,
#   в обратном порядке будет встроена старая страница (скомпилируется, но без ошибки)
deploy/build-release.sh 1.0.0     # → deploy/dist/netdisk-1.0.0-linux-amd64
scp deploy/dist/netdisk-1.0.0-linux-amd64 root@<host>:/tmp/
```

> **Без скрипта, пошагово вручную** (эквивалентно `build-release.sh`):
> Порядок ядра нельзя менять: **сначала `pnpm build` фронтенда, затем `go build`** (в обратном порядке будет встроен старый фронтенд).

```sh
# ① Окружение (внутреннее ускорение + отключение проверки)
export GOPROXY=https://goproxy.cn,direct GOSUMDB=off

# ② Сначала собрать фронтенд админ-панели (репозиторий web), и скопировать артефакт в Server-com/internal/webui/dist (для embed)
cd Server-com/web && pnpm install && pnpm build
# После размещения артефакта он упаковывается в бинарный файл инструкцией embed (web/apps/*/dist → internal/webui/dist)

# ③ Скомпилировать серверный одиночный бинарный файл
cd ../ && go build -o deploy/dist/netdisk-1.0.0-linux-amd64 ./cmd/netdisk

# ④ Скопировать на целевой сервер
scp deploy/dist/netdisk-1.0.0-linux-amd64 root@<host>:/tmp/
```

### 6.2 Развёртывание на целевом сервере

```sh
sudo bash deploy/install.sh /tmp/netdisk-1.0.0-linux-amd64 http://<внешний URL>
```

`install.sh` идемпотентен, выполняет: создание пользователя/каталогов → генерация/повторное использование secrets → установка бинарного файла и конфигурации →
установка systemd-службы → самопроверка → запуск → **самоподтверждение версии** (при успехе в последней строке печатается `INSTALL_DONE`).

> **Без скрипта, пошагово вручную** (эквивалентно `install.sh`; учётная запись службы/каталоги/пароли уже подготовлены в §3):

```sh
# ① Разместить бинарный файл и конфигурацию (владелец должен быть правильным, иначе самопроверка не пройдёт)
sudo install -o root -g netdisk -m 0755 /tmp/netdisk-1.0.0-linux-amd64 /opt/netdisk/netdisk
sudo install -o root -g netdisk -m 0644 deploy/config/config.example.yaml /etc/netdisk/config.yaml
# Если в §3 secrets не генерировались, нужно добавить (см. §3 ③); если сгенерированы — повторно использовать, не перезаписывать

# ② Установить systemd-юнит и запустить (в юните уже есть «самопроверка ExecStartPre → миграция+запуск ExecStart»)
sudo install -o root -g root -m 0644 deploy/systemd/netdisk.service /etc/systemd/system/netdisk.service
sudo systemctl daemon-reload
sudo systemctl enable --now netdisk

# ③ Подтвердить запуск
sudo systemctl is-active netdisk          # → active
sudo systemctl status netdisk -l --no-pager
```

> Важно: `ExecStart=/opt/netdisk/netdisk -migrate ...` в `netdisk.service` означает «сначала миграция, затем продолжить запуск»,
> **не завершается** — и вручную не нужно ждать его как одноразовую команду в foreground, доверьте управление systemd.

### 6.3 Миграция базы данных

Миграция записана в systemd-юнит и **выполняется автоматически при запуске службы**, запускать вручную не нужно:

```ini
ExecStartPre=/opt/netdisk/netdisk -check -config /etc/netdisk/config.yaml   # самопроверка при запуске
ExecStart=/opt/netdisk/netdisk -migrate -config /etc/netdisk/config.yaml    # сначала миграция, затем продолжить запуск
```

> Внимание: семантика `-migrate` — «сначала выполнить миграцию, затем продолжить запуск службы», **не завершается** —
> не ждите его как foreground-команду в скрипте развёртывания, иначе он зависнет навсегда.

> **Если не хотите полагаться на автоматическую миграцию systemd**, а хотите выполнить миграцию отдельно перед запуском, можно использовать goose для однократного `up` на целевой базе
> (каталог миграций в `internal/migrate/sql`; обычно не требуется, при запуске выполняется автоматически):

```sh
export NETDISK_DB_DSN='postgres://netdisk:<пароль БД>@127.0.0.1:5432/netdisk?sslmode=disable'
goose -dir internal/migrate/sql postgres "$NETDISK_DB_DSN" status   # сначала посмотреть версию
goose -dir internal/migrate/sql postgres "$NETDISK_DB_DSN" up        # выполнить миграцию
```

> Оба способа эквивалентны; пока в systemd-юните есть `-migrate`, миграция выполнится при запуске, даже без ручного запуска goose.

## 7. Настройка реверс-прокси Nginx

> Nginx — единственная внешняя точка входа, сам netdisk слушает только 127.0.0.1:8080.

```sh
# apply: установить сайт/заголовки прокси/тюнинг; verify: проверить по nginx -T (действующая конфигурация) построчно
sudo bash deploy/nginx/apply.sh
sudo bash deploy/nginx/verify.sh
```

**Несколько частых ошибок** (обработаны в скрипте, здесь объяснены причины):
- У интерфейсов загрузки/TUS должен быть отключён `proxy_request_buffering`, иначе тело запроса сначала попадёт на временный диск Nginx,
  прерывание и прогресс перестанут быть реальными;
- У интерфейса загрузки отключён `proxy_buffering`, у интерфейса SSE отключён `proxy_buffering` и увеличен `proxy_read_timeout`.

> **Без скрипта, пошагово вручную** (эквивалентно `apply.sh` + `verify.sh`):

```sh
# ① Записать конфигурацию сайта (минимально рабочая, ключевые строки отмечены)
sudo tee /etc/nginx/sites-available/netdisk >/dev/null <<'EOF'
server {
    listen 80;
    server_name <внешний домен>;

    # Общий реверс-прокси: пропускать реальный IP
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # TUS загрузка: отключить request_buffering (чтобы прерывание/прогресс были реальными)
    location /uploads/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_request_buffering off;
    }

    # WebDAV: также отключить request_buffering
    location /dav/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_request_buffering off;
        proxy_buffering off;
    }

    # SSE: отключить buffering + увеличить таймаут чтения
    location /sync/events {
        proxy_pass http://127.0.0.1:8080;
        proxy_buffering off;
        proxy_read_timeout 86400s;
    }
}
EOF

# ② Включить сайт, проверить синтаксис, перезагрузить
sudo ln -sf /etc/nginx/sites-available/netdisk /etc/nginx/sites-enabled/
sudo nginx -t                                  # продолжать только если синтаксис верен
sudo systemctl reload nginx

# ③ Вместо verify.sh: самопроверить ключевых пунктов по «действующей конфигурации» (не по файлу на диске)
sudo nginx -T | grep -E 'proxy_(request_)?buffering|proxy_read_timeout'
```

> При ручной записи чаще всего пропускают эти три настройки `proxy_*` выше; без них загрузка/прерывание/SSE будут вести себя некорректно.
> Скрипт-версия использует `deploy/nginx/verify.sh` на основе `nginx -T` для построчного утверждения этих пунктов, уже проверено за вас.

## 8. Приёмка после развёртывания

```sh
# 1) Все точки входа доступны
curl -s -o /dev/null -w '%{http_code}\n' http://<host>/admin/    # 200 «Админ-панель сетевой папки»
curl -s http://127.0.0.1:8080/healthz                            # 200

# 2) Начальный администратор создан автоматически при «инициализации базы данных»
#    Имя пользователя admin, начальный пароль admin123 (до первого запуска можно переопределить через NETDISK_BOOTSTRAP_ADMIN_PASSWORD)
#    После входа немедленно смените пароль (рекомендуется):
/opt/netdisk/bin/passwd -config /etc/netdisk/config.yaml \
  -username admin -role super_admin -prompt

# 3) Сквозной зонд: прямое подключение к приложению (не через прокси — Nginx потребляет заголовки SSE)
/opt/netdisk/bin/probesmoke -base http://127.0.0.1:8080 -user admin -pass admin123
```
