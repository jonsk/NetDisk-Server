# Server-com: повседневная эксплуатация

> В этом документе описано **как управлять после ввода в эксплуатацию**: регулярный обход, запуск/остановка, обновление, мониторинг и оповещения, устранение распространённых неполадок.
> Первую установку см. в «Установка и развёртывание» (05-INSTALL.md), защиту данных — в «Резервное копирование» (07-BACKUP.md).

---

## 1. Регулярный обход

Ниже приведён контрольный список обхода, которому можно напрямую следовать; рекомендуется проходить его ежедневно/еженедельно.

```sh
# ① Службы и зависимости работают
systemctl is-active postgresql redis-server netdisk nginx

# ② Посмотреть, нет ли аномалий в журналах
journalctl -u netdisk -n 50 --no-pager

# ③ Выполнялось ли резервное копирование недавно (критично! подробнее см. «Резервное копирование» / 07-BACKUP.md)
curl -s http://127.0.0.1:8080/metrics | grep -E 'netdisk_backup_last_success_timestamp_seconds'

# ④ Достаточно ли места на диске (при превышении 90% загрузки перестанут приниматься)
df -h /opt/netdisk/data /var/lib/postgresql /var/backups/netdisk
```

| Проверяемый пункт | Что считается нормой | При аномалии |
|---|---|---|
| Все службы active | все 4 активны | см. §6 Устранение неполадок |
| Данные PG растут, но и каталог WAL-архива тоже растёт | Архивирование нормально продвигается | Архивирование застряло = `pg_wal` заполнит диск |
| Последнее резервное копирование < 26ч | Метка времени свежая | Немедленно проверьте журнал резервного копирования |
| Обход объектов выполняется | `netdisk_object_patrol_last_timestamp_seconds` меньше 48ч назад | Остановка обхода = утечки/потери остаются незамеченными |
| Уровень диска < 90% | — | ≥90% отклоняет новые загрузки (возвращает 507) |

## 2. Порядок запуска / остановки

> Порядок важен: **сначала поднимается БД, затем приложение, последним — реверс-прокси**; при остановке — наоборот.

```sh
# Запуск
systemctl start postgresql
systemctl start redis-server
systemctl start netdisk      # При запуске автоматически довыполняется миграция БД
systemctl start nginx
systemctl is-active postgresql redis-server netdisk nginx

# Остановка (сначала остановить Nginx, затем приложение, чтобы выполняющиеся загрузки/скачивания корректно завершились)
systemctl stop nginx
systemctl stop netdisk
systemctl stop redis-server
systemctl stop postgresql
```

## 3. Обновление и откат

### 3.1 Обновление бинарника netdisk (обычное)

```sh
deploy/build-release.sh <новая версия>
scp deploy/dist/netdisk-<новая версия>-linux-amd64 root@<host>:/tmp/
# Рекомендуется использовать install.sh (идемпотентно, автоматически останавливает старый процесс → самопроверка → запуск → самоподтверждение версии)
sudo bash deploy/install.sh /tmp/netdisk-<новая версия>-linux-amd64 http://<внешний URL>
```

> Откат = установить обратно **предыдущий** бинарник и перезапустить (миграции обратно совместимы, добавочные, обычно не нужно откатывать БД).
> Если служба ранее была остановлена лимитом из-за повторяющихся падений (`systemctl start` выдаёт «Start request repeated too quickly»), после устранения коренной причины сначала выполните `systemctl reset-failed netdisk`, затем запуск.

### 3.2 Обновление мажорной версии PostgreSQL (например, 17→18)

> Базовая линия на локальной машине — 17; если на месте используется более ранняя версия (15/16) и нужно обновиться, используйте `pg_upgrade`. **Перед обновлением обязательно должна быть резервная копия, для которой проверена возможность восстановления**, поскольку при сбое `pg_upgrade` могут не подняться оба экземпляра — старый и новый.

```sh
systemctl stop netdisk                       # Сначала остановить приложение, чтобы избежать записи во время обновления
su - postgres -c "/usr/lib/postgresql/17/bin/pg_dumpall > /var/backups/netdisk/pre-upgrade.sql"
apt-get install -y postgresql-18             # Установить новую версию (источник PGDG)
su - postgres -c "/usr/lib/postgresql/17/bin/pg_upgrade \
  --old-datadir=/var/lib/postgresql/17/main --new-datadir=/var/lib/postgresql/18/main \
  --old-bindir=/usr/lib/postgresql/17/bin --new-bindir=/usr/lib/postgresql/17/bin --check"
# После прохождения --check уберите --check и повторите запуск, затем заново соберите статистику
su - postgres -c "/usr/lib/postgresql/17/bin/vacuumdb --all --analyze-in-stages"
```

## 4. Мониторинг и оповещения

- **Точка отдачи**: `GET /metrics` (текстовый формат Prometheus, собственный реализованный коллектор). По умолчанию сбор разрешён только **с локального loopback / доверенного прокси**; для межмашинного сбора настройте `NETDISK_METRICS_TOKEN` и передавайте `Authorization: Bearer <token>`.
- **Сбор**: `deploy/prometheus/prometheus.yml` (интервал по умолчанию 30s).
- **Правила оповещений**: `deploy/prometheus/netdisk-alerts.yml` (полтора десятка), проверка синтаксиса через `promtool check rules`.

**Несколько метрик, за которыми стоит следить в первую очередь** (значение + критерий):

| Метрика | Значение | Когда нужно действовать |
|---|---|---|
| `netdisk_process_resident_memory_bytes` | Резидентная память процесса | При приближении к пределу (320M) systemd убьёт и перезапустит |
| `netdisk_disk_used_percent` | Уровень диска области объектов | ≥90% отклоняет загрузки; `>85` — сначала предупреждение |
| `netdisk_backup_last_success_timestamp_seconds` | Момент последнего успешного резервного копирования | `now()-оно > 26ч` — оповещение (critical) |
| `netdisk_object_missing_total` | Количество объектов, которые есть в БД, но отсутствуют на диске | **≥1 уже означает нечитаемость данных** (critical) |
| `netdisk_object_leak_bytes` | Есть на диске, но нет в БД (занимает место) | >64MiB = диск только растёт и не уменьшается |
| `netdisk_quota_drift_bytes` | Разница между учётной квотой и реальным использованием | >1MiB = подозрение на баг расчёта квоты |
| `netdisk_restore_drill_last_timestamp_seconds` | Момент последней тренировки восстановления | Оповещение, если тренировки не было >90 дней |

> **Важный принцип**: метрика, которую не удалось считать, **не выдаёт образец**, а не сообщает 0 (сообщение 0 заставит оповещение врать). Например, при сбое зондирования ёмкости диска три кривые ёмкости исчезнут целиком — это нормальное «не удалось считать», а не переполнение диска.

## 5. Ключевые моменты сетевой безопасности и прав доступа

- Возврат `/metrics` кода **401** — это **предусмотренное поведение**: сбор разрешён только с loopback/доверенного прокси. Для межмашинного сбора обязательно передавайте Bearer token.
- Секреты никогда не попадают в yaml / репозиторий, существуют только в `/etc/netdisk/secrets.env` (ротация = изменить этот файл + перезапустить службу).
- PostgreSQL слушает только loopback, Redis слушает только loopback: порты этих двух служб **не должны появляться на сетевом интерфейсе**.

## 6. Устранение распространённых неполадок (runbook)

Каждая запись составлена по схеме **симптом → что посмотреть в первую очередь → распространённые причины и устранение**; команды можно напрямую копировать.

### 6.1 Служба не запускается

```sh
systemctl status netdisk -l
journalctl -u netdisk -n 60 --no-pager
```

| Симптом | Значение | Действие |
|---|---|---|
| `ExecStartPre ... status=1/FAILURE` | **Самопроверка при запуске заблокировала** (конфигурация/каталог/порт/зависимости) | Посмотрите полный список проблем, который она выводит за один раз, и устраните по пунктам |
| `active (running)`, но запросы дают 502 | Служба работает, но адрес прослушивания не совпадает с тем, на который указывает Nginx | Сверьте `http_addr` в конфигурации и upstream Nginx |
| `Start request repeated too quickly` | Повторяющиеся падения вызвали срабатывание лимита | После устранения коренной причины выполните `systemctl reset-failed netdisk` |

Два распространённых типа ошибок самопроверки:
- **Каталог недоступен для записи**: `chown -R netdisk:netdisk /opt/netdisk/data` (если ранее вручную от имени root создавались `objects/`, `tus-tmp/`, их владелец — root).
- **Файловая система только для чтения**: служба жёстко ограничена через `ProtectSystem=strict` — если изменили путь в secrets, необходимо **синхронно изменить `ReadWritePaths` в юните systemd**, добавив новый путь.

### 6.2 Загрузка/скачивание застряли на 0%

```sh
curl -s http://127.0.0.1:8080/metrics | grep -E 'netdisk_(http|tus|sse)'
tail -f /var/log/nginx/netdisk.access.log | grep -E 'rt=|urt='
```

- `urt=` (время вверх по течению) намного меньше `rt=` (общее время) → время тратится в Nginx → проверьте, отключено ли `proxy_request_buffering` для TUS/WebDAV (если не отключено = тело запроса сначала попадает на временный диск Nginx, и прогресс, и докачка перестают быть реальными).
- Медленное скачивание → проверьте `proxy_buffering off` для интерфейса скачивания.
- Задержка событий SSE на десятки секунд → Nginx буферизует поток событий → убедитесь, что для интерфейса SSE `proxy_buffering off` + `proxy_read_timeout 86400s`. (Все три случая проверяются утверждениями в `deploy/nginx/verify.sh`.)

### 6.3 Всех вывело из системы / вход сразу после входа обрывается

```sh
redis-cli -a <пароль> --no-auth-warning CONFIG GET appendonly appendfsync maxmemory-policy
```

- Невыполнение любого из пунктов — это аномалия — **три жёстких требования** (`requirepass` / `appendonly yes`+`everysec` / `maxmemory-policy noeviction`) и последствия отсутствия каждого см. в «Установка и развёртывание» (05-INSTALL.md) §5; сверьте по таблице по пунктам, устраните и перезапустите Redis.
- Помните: в Redis **не кэш**, теряется состояние входа и курсоры, а не файловые данные, и это не влияет на уже записанные на диск файлы.

### 6.4 Резервное копирование не выполнилось успешно

```sh
systemctl status netdisk-backup.service
journalctl -u netdisk-backup -n 40 --no-pager
cat /var/lib/netdisk/backup-status.json
su - postgres -c "psql -Atc 'SELECT archived_count, failed_count FROM pg_stat_archiver' netdisk"
ls -l /var/lib/postgresql/wal_archive | tail -3
```

- **Сбой WAL-архивирования** → девять из десяти раз причина в недостижимости каталога архива: каталог архива **нельзя** размещать в `/var/lib/netdisk` (там `netdisk:netdisk 0750`, у пользователя postgres нет прав на проход сквозь него), следует разместить в `/var/lib/postgresql/wal_archive` (собственное дерево каталогов postgres).
- **`pg_dump` Permission denied** → каталог dump должен принадлежать **postgres** (он запускается от имени postgres).

### 6.5 Оповещение обхода объектов

Обход **только для чтения**, никогда не исправляет автоматически — **до выяснения причины не удаляйте объекты вручную и не запускайте скрипты очистки**. При оповещении `object_missing` выполните воспроизведение объектов согласно «Резервное копирование» (07-BACKUP.md), чтобы локализовать проблему.

### 6.6 Диск скоро заполнится

```sh
du -sh /opt/netdisk/data /var/backups/netdisk /var/lib/postgresql/wal_archive /var/log
```

Растут три места: каталог объектов, резервные копии, WAL-архив. **Не удаляйте** каталог WAL-архива ради освобождения места (это всё, что обеспечивает возможность восстановления на момент времени). Порядок: сначала синхронизируйте резервную копию за пределы машины, затем удалите локальные старые dump (скрипт хранит 14 дней), затем рассмотрите возможность очистки меток удалённых объектов через 24-часовое окно сбора приложения (**не удаляйте вручную**).

### 6.7 Самая быстрая диагностика «ничего не делал, но просто не работает»

```sh
ss -tlnp | grep -E '80|8080|5432|6379'      # 1. Кто слушает, где слушают
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz   # 2. Обход прокси, прямое подключение
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/admin/         # 3. Затем через прокси
journalctl -u netdisk -n 20 --no-pager      # 4. Посмотреть журнал приложения (пробрасывается ли client_ip)
nginx -T | grep -A5 'location /tus'         # 5. Посмотреть «действующую» конфигурацию прокси (не файл на диске)
```

Разница между шагами 2 и 3 сразу локализует проблему — «приложение» или «прокси»; если на шаге 4 `client_ip` показывает `127.0.0.1`, а реальный клиент на другой машине, значит `X-Real-IP` не проброшен или доверенный прокси настроен неверно.
