# Документ по тестированию Server-com

> Цель: знать **какие есть тесты**, **как запускать**, **текущие фактические результаты**, **что требует ручной работы**.
> Связанные документы: `02-ARCHITECTURE.md` (архитектура), `05-INSTALL.md` (установка и развёртывание), `06-OPS.md` (повседневная эксплуатация), `07-BACKUP.md` (резервное копирование и восстановление)

---

## 1. Обзор послойного тестирования

| Слой | Что делает | Кто запускает |
|---|---|---|
| Компиляция / статическая проверка | Гарантирует компилируемость, отсутствие подозрительных конструкций | Разработка / CI, автоматически |
| Модульные + интеграционные тесты | Проверка бизнес-правил по функциям / интерфейсам | Разработка / CI, автоматически |
| Контроль архитектурной дисциплины | Гарантирует слоистость, красные линии, согласованность документации | CI, автоматически |
| Контроль покрытия | Гарантирует, что ключевые пакеты не остаются без тестов | CI, автоматически |
| Сквозные зонды | Реальный дымовой тест полного HTTP-пути | После развёртывания / перед релизом, нужна реальная машина |
| Производственный базис | Проверка списка / синхронизации / конкурентной пропускной способности | Реальная машина, повторяемый скрипт |
| Ручная приёмка | Клики UI, сверхдлинные пути, реальные платформы и т.д. | Эксплуатация / приёмщики |

> В проекте `cmd/testsgate`, `cmd/depsguard`, `cmd/coveragegate` — это **независимые контрольные программы**.
> Локальные команды и команды CI — это одни и те же команды (CI использует те же самые команды).

## 2. Автоматические контрольные пороги (одна команда — один слой)

Выполняется в корневом каталоге репозитория (`Server-com/`):

| Слой | Команда | Что блокирует |
|---|---|---|
| Компиляция / статическая | `go build ./... && go vet ./...` | Ошибки компиляции, подозрительные конструкции |
| Модульные + интеграционные | `NETDISK_TEST_DSN='...' go test ./... -count=1` | Все Go-кейсы (включая реальные PG/Redis) |
| Интеграция не пропущена | `go run ./cmd/testsgate` | «Группа пропущена из-за отсутствия DSN, а CI весь зелёный» — такой **ложный зелёный**, называет любой пропущенный кейс |
| Состязание данных | `go run ./cmd/testsgate -race` | Состязание данных (требуется gcc) |
| Архитектура и дисциплина документации | `go run ./cmd/depsguard` | Ядро-пакеты зависят от HTTP-слоя / дисциплина клиента / красные линии / согласованность документации и эксплуатационных артефактов |
| Покрытие | `go run ./cmd/coveragegate -profile <cover.out> -min 55` | Покрытие ключевого пакета упало ниже порога |
| Сквозной зонд | `go run ./cmd/probesmoke -pass <пароль>` | Реальный HTTP полный путь (загрузка/скачивание/шаринг/WebDAV/аудит/обход…) |

> Интеграционным тестам нужна БД `netdisk_test` + Redis. Без реальных PG/Redis интеграционные кейсы пропускаются;
> задача `testsgate` — **следить, не пропущен ли какой-либо кейс тайком**, чтобы в CI не возник ложный зелёный.

## 3. Модульные + интеграционные тесты (текущее состояние)

- Полный прогон **1042 кейса пройдено**, покрыто 39 пакетов / **0 пропущено** (проверено именным перечнем `testsgate`).
- Области покрытия: токен аутентификации / финализирование загрузки / конкурентность объектной блокировки / семантика каталога / синхронизация изменений / шаринг / сверка квот / обход / WebDAV.

**Послойные критерии для чувствительных к производительности утверждений** (например, P95 окна конкурентной блокировки финализирования):
- Основной критерий — **медиана** (регрессия заставит каждое удержание блокировки замедлиться);
- Хвост использует P95 < 500мс (поглощает «параллелизм всех пакетов + общая тестовая БД» дрожание машины).
- Проверка от противного: искусственный sleep в критической секции блокировки → медиана сразу замедляется, кейс краснеет, что означает «критическая секция расширилась», а не «дрожание».

## 4. Сквозной зонд (probesmoke)

Одна команда выполняет дымовой тест полного пути на **работающей реальной службе** (51+ шагов): вход → каталог → загрузка (TUS/WebDAV/multipart) →
скачивание/Range → шаринг → события синхронизации → аудит → обход.

```sh
go run ./cmd/probesmoke -base http://127.0.0.1:8080 -user admin -pass '<пароль>'
```

> При прохождении через прокси заголовки SSE поглощаются Nginx (`X-Accel-Buffering`), поэтому **зонд должен подключаться к приложению напрямую** (51/51 все проходят);
> при прохождении через прокси результат 50/51, и это различие объяснено (не является сбоем).

## 5. Производственный базис (фактические замеры 2026-09-12)

Скрипт: `deploy/verify/06-perf-baseline.sh` (самодостаточный, повторяемый, цифры выводятся фактическим замером скрипта). Машина: Debian 13,
6 vCPU / ~2ГБ RAM / последовательная запись 2723.6 МБ/с (локальный базис).

| Точка приёмки | Порог | Фактический замер | Вывод |
|---|---|---|---|
| Список каталога 100 тыс. строк | P95 ≤ 500мс | **P95 107.2 мс** (страница по умолчанию limit=200) | Пройдено (запас ок. 4.7 раза) |
| Восприятие удалённого изменения (видно через `/changes`) | P95 ≤ 3с | **P95 78.1 мс** (multipart-запись) | Пройдено (запас ок. 37 раз) |
| Восприятие удалённого изменения (кадр SSE достиг) | P95 ≤ 3с | **P95 80.5 мс** | Пройдено |
| Конкурентная загрузка 8×8МиБ | — | **9.66 МБ/с**, успешно 8/8, сбоев 0 | Пройдено |
| Конкурентная загрузка 16×8МиБ | — | **10.57 МБ/с**, успешно 16/16, сбоев 0 | Пройдено (12 раз ограничено скоростью, затем повтор) |
| Конкурентное скачивание 8/16×8МиБ | — | **1944 / 2580 МБ/с** | Пройдено (попадание в page cache, нельзя считать дисковой пропускной) |

> **Честное пояснение**: при конкурентной загрузке 16 `POST /tus` 12 раз получал **429 ограничение скорости** сервером (`rate_limits.upload=10/s`),
> скрипт после экспоненциальной задержки повторил и все прошли успешно — это **ограничение скорости работает по замыслу**, а не сбой загрузки. Если приёмка требует «16 конкурентных за один раз все проходят»,
> нужно увеличить `rate_limits.upload` или снизить конкурентность. Скачивание на уровне 2ГБ/с — это скорость «память + виртуальный диск», лишь показывает отсутствие очереди и ошибок на пути скачивания при конкурентности.

### Способ воспроизведения

```sh
BASE=http://127.0.0.1:8080 USER=admin PASS='<пароль>' \
ROWS=100000 NREP=60 NFEED=30 SAR="8 16" UPFILE=8388608 \
sudo sh deploy/verify/06-perf-baseline.sh | tail -n +1
```

В конце скрипт печатает (пообразцово / гистограмма / квантили / строка вердикта). По умолчанию данные зонда очищаются автоматически; `KEEP=1` сохраняет их (для диагностики).

## 6. Точки сверки приёмки и повторного запуска

| Область приёмки | Точка повторного запуска |
|---|---|
| Базис модульных тестов / покрытие | `go test ./... -coverprofile=cover.out` → `coveragegate` |
| Интеграционные тесты по пунктам | `go test -tags=integration ./...` |
| Производственный базис | `deploy/verify/06-perf-baseline.sh` (реальная машина) |
| Развёртывание и обновление | `deploy/verify/0[12567]-*.sh` (скрипты реальной машины по пунктам) |
| Резервное копирование / восстановление / PITR | `deploy/backup/*.sh` (скрипты тренировки + журнал) |
| Мониторинг и оповещения | `curl /metrics`, `promtool check rules` |
| Согласованность объектов / сбор временных файлов | `go test ./internal/storage/ -run 'ReapTemp|MismatchedObjectKeys' -count=1 -v` |
| Состязание данных | `go run ./cmd/testsgate -race` |

## 7. Пункты, всё ещё требующие ручного выполнения (не имитировать покрытие в автоматизации)

| Пункт | Почему автоматизация не покрывает | Место регистрации |
|---|---|---|
| Сверхдлинный путь на Windows в реальных условиях | Нужен реальный диск и среда с действующим `longPathAware` | Чек-лист приёмки клиента |
| Поведение повтора при блокировке файла антивирусом | Нужен реальный перехват AV | То же (честно отметить «не проверено») |
| Клики интерфейса (вход/трей/настройки/конфликт/удалённый обзор/проверка обновлений) | Нет автоматизации UI | Чек-лист приёмки клиента |
| 24-часовой долгий прогон клиента | Длительность и реальная интерактивная сессия | Ручное выполнение перед релизом |
| Тренировка третьей стороной по инструкции (резервное копирование/восстановление) | Нужен «другой человек», действующий по инструкции | Журнал тренировок |

## 8. Три дисциплины тестирования

1. **Невозможность определить ≠ пройдено**: проверяющий при «невозможности определить» должен вынести решение о сбое, его нельзя считать пройденным.
2. **Проверка от противного — часть утверждения**: для каждого ключевого утверждения нужно один раз «испортить код → утверждение должно покраснеть»,
   иначе вы не знаете, за чем следите (в репозитории неоднократно случалось «испортили, а зелёный остался»).
3. **Доказательства должны воспроизводиться**: доказательство = команда + реальный вывод + версия на тот момент; вставка вывода без указания источника команды не считается доказательством.
