# Server-com 日常运维

> 本文讲**上线之后怎么管**：例行巡检、启停、升级、监控告警、常见故障排查。
> 首次安装见《安装与部署》，数据保护见《备份与恢复》。

## 1. 例行巡检

下面是一份可直接照做的巡检清单，建议每日/每周过一遍。

```sh
# ① 服务与依赖都在跑
systemctl is-active postgresql redis-server netdisk nginx

# ② 看日志有没有异常
journalctl -u netdisk -n 50 --no-pager

# ③ 备份是否最近成功过（关键！详见《备份与恢复》）
curl -s http://127.0.0.1:8080/metrics | grep -E 'netdisk_backup_last_success_timestamp_seconds'

# ④ 磁盘是否够用（超过 90% 就拒收上传了）
df -h /opt/netdisk/data /var/lib/postgresql /var/backups/netdisk
```

| 检查项 | 怎么算正常 | 异常时 |
|---|---|---|
| 服务全部 active | 4 个都是 active | 见 §6 故障排查 |
| PG 数据在涨但 WAL 归档目录也在涨 | 归档正常推进 | 归档卡住 = `pg_wal` 会涨满磁盘 |
| 最近一次备份 < 26h | 时间戳是最近的 | 立刻查备份日志 |
| 对象巡检在跑 | `netdisk_object_patrol_last_timestamp_seconds` 距今 <48h | 巡检停摆 = 泄漏/丢失无人观测 |
| 磁盘水位 < 90% | — | ≥90% 拒绝新上传（返回 507） |

## 2. 启动 / 停止顺序

> 顺序有讲究：**数据库先起、应用后起、反向代理最后起**；停止时反过来。

```sh
# 启动
systemctl start postgresql
systemctl start redis-server
systemctl start netdisk      # 启动时会自动补齐数据库迁移
systemctl start nginx
systemctl is-active postgresql redis-server netdisk nginx

# 停止（先停 Nginx 再停应用，让进行中的上传/下载优雅排空）
systemctl stop nginx
systemctl stop netdisk
systemctl stop redis-server
systemctl stop postgresql
```

## 3. 升级与回滚

### 3.1 升级 netdisk 二进制（常规）

```sh
deploy/build-release.sh <新版本>
scp deploy/dist/netdisk-<新版本>-linux-amd64 root@<host>:/tmp/
# 推荐走 install.sh（幂等，自动停旧进程→自检→启动→版本自证）
sudo bash deploy/install.sh /tmp/netdisk-<新版本>-linux-amd64 http://<对外URL>
```

> 回滚 = 把**上一个**二进制 `install` 回去再重启（迁移是向前兼容的追加式，一般无需回退库）。
> 若服务曾因反复崩溃被限流停（`systemctl start` 报 "Start request repeated too quickly"），
> 修好根因后先 `systemctl reset-failed netdisk` 再启动。

### 3.2 升级 PostgreSQL 大版本（如 17→18）

> 本机基线是 17；若现场升级到更高主版本，用 `pg_upgrade`。**升级前必须有一次验证过能恢复的备份**，
> 因为 `pg_upgrade` 失败时新旧两个实例都可能起不来。

```sh
systemctl stop netdisk                       # 先停应用，避免升级期间写入
su - postgres -c "/usr/lib/postgresql/17/bin/pg_dumpall > /var/backups/netdisk/pre-upgrade.sql"
apt-get install -y postgresql-18             # 装新版本（PGDG 源）
su - postgres -c "/usr/lib/postgresql/17/bin/pg_upgrade \
  --old-datadir=/var/lib/postgresql/17/main --new-datadir=/var/lib/postgresql/18/main \
  --old-bindir=/usr/lib/postgresql/17/bin --new-bindir=/usr/lib/postgresql/17/bin --check"
# --check 通过后再去掉 --check 重跑，然后重新收集统计信息
su - postgres -c "/usr/lib/postgresql/17/bin/vacuumdb --all --analyze-in-stages"
```

## 4. 监控与告警

- **暴露点**：`GET /metrics`（Prometheus 文本格式，**自己实现**的采集器）。
  默认只允许**本机回环 / 可信代理**抓取；跨机抓取要配 `NETDISK_METRICS_TOKEN` 并带 `Authorization: Bearer <token>`。
- **抓取**：`deploy/prometheus/prometheus.yml`（默认 30s 间隔）。
- **告警规则**：`deploy/prometheus/netdisk-alerts.yml`（十几条），用 `promtool check rules` 校验语法。

**最该盯住的几条指标**（含义 + 判据）：

| 指标 | 含义 | 什么时候要动 |
|---|---|---|
| `netdisk_process_resident_memory_bytes` | 进程常驻内存 | 接近上限（320M）会被 systemd 杀掉重启 |
| `netdisk_disk_used_percent` | 对象区磁盘水位 | ≥90% 拒收上传；`>85` 先预警 |
| `netdisk_backup_last_success_timestamp_seconds` | 最近一次备份成功时刻 | `now()-它 > 26h` 告警（critical） |
| `netdisk_object_missing_total` | 库里有、盘上没的对象数 | **≥1 就是数据不可读**（critical） |
| `netdisk_object_leak_bytes` | 盘上有、库里没有（占空间） | >64MiB = 磁盘只涨不跌 |
| `netdisk_quota_drift_bytes` | 配额账面与真实用量之差 | >1MiB = 配额计算疑似有 bug |
| `netdisk_restore_drill_last_timestamp_seconds` | 最近一次恢复演练时刻 | >90 天未演练要告警 |

> **重要原则**：读不到的指标会**不出样本**而不是报 0（报 0 会让告警说假话）。
> 比如磁盘容量探测失败时，三条容量曲线会整段消失——这是正常的"读不到"，不是磁盘满了。

## 5. 网络安全与权限要点

- `/metrics` 返回 **401** 是**设计行为**：它只允许回环/可信代理抓取。跨机器抓取必须带 Bearer token。
- 密钥永不进 yaml / 版本库，只存在于 `/etc/netdisk/secrets.env`（轮换 = 改这个文件 + 重启服务）。
- PostgreSQL 只监听回环、Redis 只监听回环：这两个服务的端口**不应出现在网卡上**。

## 6. 常见故障排查（runbook）

每条按 **症状 → 先看什么 → 常见原因与处置** 写，命令可直接照贴。

### 6.1 服务起不来

```sh
systemctl status netdisk -l
journalctl -u netdisk -n 60 --no-pager
```

| 症状 | 含义 | 处置 |
|---|---|---|
| `ExecStartPre ... status=1/FAILURE` | **启动自检拦住**（配置/目录/端口/依赖） | 看它一次列全的问题清单，逐项修 |
| `active (running)` 但请求 502 | 服务在，但监听地址与 Nginx 指向的不符 | 对照配置里的 `http_addr` 与 Nginx upstream |
| `Start request repeated too quickly` | 反复崩溃触发限流 | 修根因后 `systemctl reset-failed netdisk` |

常见两类自检报错：
- **目录不可写**：`chown -R netdisk:netdisk /opt/netdisk/data`（若曾用 root 手工建过 `objects/`、`tus-tmp/`，它们的属主是 root）。
- **只读文件系统**：服务被 `ProtectSystem=strict` 限死——改过 secrets 里的路径，必须**同步改 systemd 单元的 `ReadWritePaths`**，把新路径加进去。

### 6.2 上传/下载卡在 0%

```sh
curl -s http://127.0.0.1:8080/metrics | grep -E 'netdisk_(http|tus|sse)'
tail -f /var/log/nginx/netdisk.access.log | grep -E 'rt=|urt='
```

- `urt=`（上游耗时）远小于 `rt=`（总耗时）→ 时间花在 Nginx 上 → 检查 TUS/WebDAV 是否**关掉了 `proxy_request_buffering`**（没关 = 请求体先落 Nginx 临时盘，进度和续传都不真实）。
- 下载慢 → 检查下载接口的 `proxy_buffering off`。
- SSE 事件延迟几十秒 → Nginx 缓冲了事件流 → 确认 SSE 接口 `proxy_buffering off` + `proxy_read_timeout 86400s`。
  （这三条 `deploy/nginx/verify.sh` 都有断言。）

### 6.3 所有人都被登出 / 登录后立刻掉线

```sh
redis-cli -a <口令> --no-auth-warning CONFIG GET appendonly appendfsync maxmemory-policy
```

- 任何一项不满足都是异常——**三条硬性要求**（`requirepass` / `appendonly yes`+`everysec` / `maxmemory-policy noeviction`）
  及各自缺项后果见《安装部署》§5，按表逐项对照修复后重启 Redis。
- 记住：Redis 里**不是缓存**，丢的是登录态和游标，不是文件数据，也不影响已落盘的文件。

### 6.4 备份没跑成功

```sh
systemctl status netdisk-backup.service
journalctl -u netdisk-backup -n 40 --no-pager
cat /var/lib/netdisk/backup-status.json
su - postgres -c "psql -Atc 'SELECT archived_count, failed_count FROM pg_stat_archiver' netdisk"
ls -l /var/lib/postgresql/wal_archive | tail -3
```

- **WAL 归档失败** → 十有八九是归档目录不可达：归档目录**不能**放在 `/var/lib/netdisk` 下
  （那是 `netdisk:netdisk 0750`，postgres 用户没有穿越权限），应放在 `/var/lib/postgresql/wal_archive`
  （postgres 自己的目录树）。
- **`pg_dump` Permission denied** → dump 目录必须属于 **postgres**（它以 postgres 身份运行）。

### 6.5 对象巡检告警

审计是**只读**的，绝不会自动修复——**查清原因前不要手工删对象、不要跑清理脚本**。
`object_missing` 告警时，按《备份与恢复》做对象回放来定位。

### 6.6 磁盘将满

```sh
du -sh /opt/netdisk/data /var/backups/netdisk /var/lib/postgresql/wal_archive /var/log
```

三处都会涨：对象目录、备份、WAL 归档。**不要**为了腾空间删 WAL 归档目录
（那是时间点恢复能力的全部）。顺序：先把备份同步出机再删本地旧 dump（脚本保留 14 天），
再考虑让应用的 24h 回收窗口清理已删除对象的墓碑（**不要手工删**）。

### 6.7 "什么都没做但就是不通"的最省时排查

```sh
ss -tlnp | grep -E '80|8080|5432|6379'      # 1. 谁在监听、监听在哪
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz   # 2. 绕过反代直连
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/admin/         # 3. 再经反代
journalctl -u netdisk -n 20 --no-pager      # 4. 看应用日志（client_ip 是否透传）
nginx -T | grep -A5 'location /tus'         # 5. 看反代"生效"配置（不是磁盘上的文件）
```

第 2、3 步的差异能立刻把问题定位到"应用"还是"反代"；
第 4 步若 `client_ip` 显示 `127.0.0.1` 而实际客户端在别的机器，说明 `X-Real-IP` 没透传或可信代理配错。
