# Server-com 备份与恢复

> 核心目标一句话：**任意时刻都能把"数据库 + 对象"恢复到同一时间点**。
> 配套脚本在 `deploy/backup/`，由 systemd 定时器自动驱动。

---

## 1. 备份目标与策略

网盘有两类数据，**必须能一起恢复到同一时刻**：

1. **元数据**（PostgreSQL 里的用户/空间/目录项/配额…）；
2. **对象文件**（真正的内容，按内容哈希存在本地磁盘）。

只备份其一而不备份另一个，会得到"文件在但库指向别的对象"或"文件全 0 字节"的错乱状态。

| 数据 | 方式 | 频率 | 保留 |
|---|---|---|---|
| PostgreSQL | `pg_dump -Fc`（每日整库备份）+ **WAL 归档**（实现时间点恢复） | 整库每日 02:30；WAL 实时 | dump 14 天 |
| 对象目录 `/opt/netdisk/data` | borg（去重增量） | **每 4 小时** | 7 日 / 4 周 / 6 月 |
| Redis（AOF） | 随对象目录一起进备份 | 同上 | 同上 |

两个定时器自动触发（都由 `deploy/backup/netdisk-backup.sh` 驱动）：

```sh
netdisk-backup.sh full      # 每日：WAL 自检 + 对象增量 + PG 整库 + 验读 + 保留清理
netdisk-backup.sh objects   # 每 4 小时：只做对象目录增量
```

### 备份实现里的三个"防失效"设计

1. **备份完立刻验读**：`pg_restore --list <dump>` 打不开就判失败——只写不验的备份，只是一个"你以为存在"的文件。
2. **WAL 归档看"新增失败"而不是"是否为零"**：`failed_count` 是累计值、永不复位。
   判"是否为 0"会让历史上一次失败变成"备份从此永远失败"。现改为记录基线、只对**增量**告警。
3. **状态 JSON 原子写**（临时文件 + `mv`）：避免 Prometheus 抓到写了一半的文件。
   "备份状态未知"和"备份失败"是两件完全不同的事故。

## 2. 备份真的能恢复吗？——恢复演练

> 备份 ≠ 能恢复。真正的验证是**恢复演练**：季度一次，`deploy/backup/netdisk-restore-drill.sh`。

演练做四件事，**任何一件失败都算演练失败**：

1. 把最近一次备份**恢复到一个独立的临时库**（`netdisk_drill_<日期>`，**绝不碰生产库**）；
2. **关键表行数比对**生产 vs 恢复库（users/spaces/files/file_objects/space_members/sync_feed/audit_logs）；
3. **对象目录回放**：从备份恢复到临时目录，对存活对象逐个比对内容哈希（sha256）；
4. 写入演练时刻，超 **90 天未演练**就告警。

```sh
sudo /opt/netdisk/bin/netdisk-restore-drill.sh     # 记录在 /var/backups/netdisk/logs/drill-<日期>.log
```

> 必须至少留一个存活对象，否则演练只能验证"归档能解压"、验证不了"内容能回放"
> （恢复出 0 字节的文件一样"存在"）。可用 WebDAV 直传造一个：
> `curl -u admin:<口令> -T <本地文件> http://127.0.0.1:8080/webdav/<space_id>/<文件名>`
> （路径**必须带 space_id**）。

## 3. 时间点恢复（PITR）：恢复到某个时刻

> 前提：`archive_mode=on` + `archive_command` 正常（安装时已配好），且**有一份基础物理备份**可作起点。

```sh
# ① 取一份基础备份（物理备份，配合 WAL 才能"回到过去"）
su - postgres -c "/usr/lib/postgresql/17/bin/pg_basebackup -D /var/backups/netdisk/base -Ft -z -X fetch"

# ② 还原到一个"独立实例目录"（不要覆盖生产数据）
install -d -o postgres -g postgres -m 0700 /var/lib/postgresql/17/restore
tar -xzf /var/backups/netdisk/base/base.tar.gz -C /var/lib/postgresql/17/restore

# ③ 写恢复目标（恢复到 2026-09-12 19:53 这个时刻）
cat >> /var/lib/postgresql/17/restore/postgresql.auto.conf <<'EOF'
restore_command = 'cp /var/lib/postgresql/wal_archive/%f %p'
recovery_target_time = '2026-09-12 19:53:00+08'
recovery_target_action = 'promote'
EOF
touch /var/lib/postgresql/17/restore/recovery.signal
chown -R postgres:postgres /var/lib/postgresql/17/restore

# ④ 用另一个端口起恢复实例（与生产并存，不动生产）
su - postgres -c "/usr/lib/postgresql/17/bin/pg_ctl -D /var/lib/postgresql/17/restore \
  -o '-p 5433' -l /tmp/pitr.log start"
su - postgres -c "psql -p 5433 -Atc 'SELECT count(*) FROM files' netdisk"
```

**PITR 演练脚本**（`netdisk-pitr-drill.sh`）把这套自动化并真的"做一次时间旅行"，
判据不是"库能起来"，而是**目标时刻之后的数据必须不在**：
插入 `before`(T0) → 取物理备份 → 记录目标时刻 T → 插入 `after`(T1>T) →
从备份恢复到 T → 断言：库中 `before` 存在、`after` **不存在**。

实操要点：
- 基础备份用 **plain 格式**（`-Fp`，直接落成可用数据目录）比 `-Ft`（压缩打包）省事；
- 恢复实例的 `max_connections` 等参数**必须 ≥ 主库**，否则 PG 直接拒绝恢复；
- 要在**副本**上演练：promote 之后那个目录就被写过了，不再是"那一刻的备份"，
  基础备份是制品，演练只能动它的副本。

## 4. 对象文件回放（单独做）

```sh
export BORG_REPO=/var/backups/netdisk/borg BORG_PASSPHRASE=$(cat /etc/netdisk/borg.passphrase)
borg list --last 3 "$BORG_REPO"                  # 看最近几份
cd /tmp/restore && borg extract "$BORG_REPO::full-2026-09-12T19:53:38"
# 恢复出来形如 /tmp/restore/opt/netdisk/data/objects/xx/yy/<sha256>
```

> **对象与库必须来自同一时刻**：只回放对象不回放库 = "文件在但库指向别的对象"；
> 只回放库不回放对象 = "文件全 0 字节"。演练脚本把两者绑在一起做，正是为了防这件事。

## 5. Redis 的 AOF

Redis 里存的是登录态与游标（**不是缓存**，持久化必须开的"三条硬性要求"见《安装部署》§5）。本节要点是把 AOF 也一并备份出去：

```sh
redis-cli -a <口令> --no-auth-warning BGREWRITEAOF      # 手工触发一次 AOF 重写
ls -l /var/lib/redis/appendonlydir/                     # AOF 与 manifest 落在这里
```

备份方式：随对象目录一起进 borg，或每日 `BGREWRITEAOF` 后单独 `cp`。**AOF 丢了 → 所有用户重新登录**（数据不丢）。

## 6. 对应告警

与备份/恢复强相关的告警（规则见 `deploy/prometheus/netdisk-alerts.yml`，指标判据详见《日常运维》§4）：

- `NetdiskBackupStale` / `NetdiskObjectsBackupStale`：整库/对象备份超过预期频率没成功；
- `NetdiskWalArchiveFailing`：WAL 归档持续失败，`pg_wal` 会涨满磁盘；
- `NetdiskRestoreDrillOverdue`：距上次演练 > 90 天，该做恢复演练了。

## 7. 目前尚未做（如实标注）

- **每周基础物理备份**（PITR 的"起点"）。当前 `netdisk-backup.sh` 只做 `pg_dump`（逻辑备份），
  不产出物理基础备份——所以能"回到过去"的范围受限于手工演练留下的那份基础备份。
  建议上线前加一个**每周 `pg_basebackup` 定时器**（保留 4 份）。
- **异地副本**。目前所有备份副本都在同一块磁盘上，**磁盘坏 = 数据与备份一起没**，
  这是当前方案最大的单点。建议加 borg 远端仓库或对象存储副本，把备份同步出本机。
