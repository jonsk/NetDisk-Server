## 1. 概述与定位

`Server-com` 是一个**网盘的服务端**，使用 **Go** 写成，最终编译成**一个可执行文件**（单二进制）。
它提供团队共享空间、多协议上传（TUS / WebDAV / multipart）、版本化定稿、实时同步感知、
细粒度权限与配额治理，既可部署为私有网盘，也能作为企业的文件中枢。

社区版（Server-com）只保留**密码登录 + 管理后台**，是商业版（Server-Ent）的功能子集。

**核心心智：整个服务就是一个"大箱子"，外面有四个组件在配合它。**

## 2. 总体架构

### 2.1 部署组成（四件套）

| 组件 | 作用 | 备注 |
|---|---|---|
| **netdisk**（本仓库产物） | 收 HTTP 请求、处理业务、读写元数据与对象 | 同一个二进制承载 REST / WebDAV / TUS / SSE / 内嵌管理后台 |
| **PostgreSQL 17（最低支持）** | 唯一元数据引擎（所有"目录项/用户/空间/配额"都在这） | 含 WAL 归档用于时间点恢复。**最低 17**：主键默认值用 `gen_random_uuid()`（PG 13 起内置），版本下限不卡在 UUID 上，最低支持定 17（对齐主流发行版自带版本）。版本要求详见《安装部署》§1 |
| **Redis** | 会话（token）/ 限速窗口 / 变更流游标 / 任务队列 | **不是缓存**，丢了 token 就全体登出 |
| **Nginx** | 反向代理，单端口对外 | 生产才需要；开发可直接访问应用 |

```
                       ┌──────────────────────────────────────┐
  Web 管理后台 /admin ─▶│                                      │
  WebDAV 客户端  ─WebDAV▶│        netdisk (Go 单二进制)          │
  TUS 上传器      ─TUS─▶│   REST · TUS · WebDAV · SSE 统一入口  │
  桌面同步客户端  ─SSE──▶│                                      │
                       │   ┌──────────────────────────────┐   │
                       │   │ finalize 唯一写路径 + 对象锁   │   │
                       │   │ 内容寻址 → 本地磁盘对象存储     │   │
                       │   └──────────────────────────────┘   │
                       └───────────┬──────────────────────────┘
                                   │
                     ┌─────────────┼─────────────┐
                     ▼             ▼             ▼
               ┌──────────┐  ┌────────┐   ┌────────────┐
               │PostgreSQL│  │ Redis  │   │Nginx(反代) │
               │  元数据   │  │会话/限速│   │  单端口    │
               └──────────┘  └────────┘   └────────────┘
```

### 2.2 为什么单二进制 + 内嵌前端

管理后台前端由 web 仓库构建后，产物被**编译期嵌进** Go 二进制（`internal/webui/dist/`），
由 Go 通过 `embed` 直接提供（`/admin`）。好处：分发一个文件即可，无需在服务器上单独部署前端静态站。

> ⚠️ 因此**改了前端必须重新编译 Go 二进制**：先 `pnpm build` 再 `go build`，
> 顺序反了会嵌入旧产物（能编译、页面却是旧版，且不报错）。

## 3. 分层架构（internal 包划分）

代码按职责分成 5 个层次，上层只允许依赖下层（由 `depsguard` 机械校验）：

```
┌─────────────────────────────────────────────────────────────┐
│ 4. 入口层   cmd/  (netdisk / migrate / passwd / depsguard …)  │
├─────────────────────────────────────────────────────────────┤
│ 3. 接口层   internal/api/  (HTTP handler、路由、中间件)          │
│            internal/webdavfs/ webdavauth/                     │
├─────────────────────────────────────────────────────────────┤
│ 2. 业务层   usersvc/orgsvc/spacesvc/filesvc/sharesvc/ │
│            uploadsvc/finalize/lifecycle/syncfeed/syncsse/    │
│            patrol/quotareconcile/consistency/credentials/    │
├─────────────────────────────────────────────────────────────┤
│ 1. 领域/数据  repo/(数据访问) model/(领域模型) objlock/ storage/  │
│            authsvc/ cache/ auth/ apierr/reqctx/middleware/    │
├─────────────────────────────────────────────────────────────┤
│ 0. 底座      config/ db/ migrate/ ratelimit/ namepolicy/      │
│            dirops/ fastupload/ condreq/ webui/ obs/ syncssem  │
└─────────────────────────────────────────────────────────────┘
```

**纪律（红线 R-xx 的核心）**：`objlock`（锁）、`storage`（对象存储）、`model`（领域模型）等
"内核包"**绝不允许依赖 `internal/api`（HTTP 层）**。业务逻辑必须与 HTTP 解耦，
这样即使换一种接入方式（WebDAV/TUS/内部调用）业务规则也不变。

## 4. 核心设计机制

### 4.1 finalize —— 唯一写路径

所有上传（TUS 分片、WebDAV PUT、multipart 直传）最终**都汇入同一条定稿逻辑** `finalizeUpload()`：
1. 先校验秒传（内容哈希已存在则直接复用，防"投毒"）；
2. 把内容写进对象区并拿到**内容寻址**对象；
3. 短事务里写入目录项与引用计数；
4. 写变更流（sync_feed）触发同步感知。

好处：三条上传通道的行为完全一致，杜绝"某条通道绕过某条规则"的漏洞。

### 4.2 内容寻址对象存储

对象按**内容哈希**存放，路径形如 `objects/xx/xx/<sha256>`：
- **同内容只存一份**（天然去重）：两个用户传同一个文件，磁盘只放一份；
- 文件名与内容分离：改文件名不复制数据，改的是元数据；
- 不可变对象：定稿后的内容不再被改写，杜绝"静默覆盖/文件漂移"。

### 4.3 对象级双层锁（ADR-2）

为防多个请求同时定稿/删除同一个对象导致数据错乱，引入对象级锁：

| 级别 | 用途 | 持锁方式 |
|---|---|---|
| **会话级锁** | 定稿全程、生命周期 worker（真正的写路径） | 单条专用数据库连接贯穿，持锁有上限（封顶），防临界区过长 |
| **事务级锁** | 纯引用 +1（复制、共享到空间） | 只在一次短事务内持有 |

锁键由对象哈希决定，加锁顺序按哈希升序，避免死锁。

### 4.4 双态同步（SSE + 游标）

桌面客户端需要"远端一变我就知道"：
- **SSE 推送**（`/sync/events`）：实时把变更推给在线客户端（快，但可能丢帧）；
- **游标拉取**（`/changes`）：客户端带游标（`since`）增量拉取（可靠，兜底）。

两者共用**同一个全局 `change_seq`**（一张 `sync_feed` 表，全局递增序号），
客户端可两者交替使用、以 `/changes` 为准补拉。这样既省掉周期性全量扫描，又不会丢变更。

### 4.5 JWT 分端认证

登录成功后签发 JWT（HS256），分两端：
- **web 端**（管理后台）与 **desktop 端**（桌面客户端）令牌独立（R-14），
  避免一处泄露影响全身；
- 访问刷新令牌存 Redis，支持吊销与"单飞刷新"（同一时刻只有一个刷新请求成功）。

社区版只保留**账密登录**（`/api/v1/auth/login`）。

### 4.6 目录语义与命名约束

- 目录深度 ≤ 31 层 且 单个累计路径 ≤ 240 字节（双上限，可配置）；
- 文件名大小写不敏感判重（`lower(name)` + 唯一索引）；
- 目录级"移动/删除子树"超过阈值（默认 1000 行）转**异步任务**，返回 `task_id` 供客户端轮询。

## 5. 数据模型（核心表）

| 表 | 含义 |
|---|---|
| `users` | 用户（账密哈希、邮箱、显示名、角色） |
| `organizations` / `departments` / `groups` | 组织 / 部门 / 群组 |
| `spaces` | 空间（个人空间 + 团队空间；含配额 `used_bytes`、`last_seq`） |
| `space_members` | 空间成员与权限 |
| `files` | 目录项（文件与目录；`is_dir`、`parent_id`、`name`、`depth`、`size`） |
| `file_objects` | 内容寻址对象（哈希、四态：live/pending_delete…、引用计数 `ref_count`） |
| `sync_feed` | 变更流（全局 `change_seq`、90 天保留） |
| `shares` | 分享链接（token、权限、过期） |
| `audit_logs` | 审计日志（当前为预留占位，不在社区版持久化） |

## 6. 配置设计

- **默认值只有一份**：在 Go 结构体 `internal/config.Default()` 里；删除配置段不会变成零值，而是回落到默认；
- **secret 绝不进 yaml**：`JWT_SECRET`、数据库口令、Redis 口令只走**环境变量**（`NETDISK_*`）；
- 优先级：Go 默认 < 配置文件 < 环境变量；
- 启动自检（`netdisk -config ... -check`）：任何非法项**一次性列全**并以非 0 退出，而不是等第一次请求才 500；
- 时长用可读写法（`5m`/`30s`/`24h`）。

## 7. 关键流程

### 7.1 一次上传（TUS）的生命周期

```
客户端 ─PATCH 分片→ 暂存区(tus-tmp) ─全部传完→ finalizeUpload()
    finalize: 计算哈希 → 秒传去重检查 → 写对象区(objects/) → 短事务写 files+file_objects
             → 写 sync_feed(change_seq++) → 推 SSE → 返回 X-File-Id 完成
```

### 7.2 一次请求的处理链

```
Nginx ─→ 中间件链(日志/恢复/限速/认证) ─→ 路由(ServeMux) ─→ handler ─→ 业务 service ─→ repo(DBA)
```

## 8. 接口入口总览

| 入口 | 说明 |
|---|---|
| `REST /api/v1/*` | 认证、用户、部门、空间、文件、目录、上传、下载、分享、变更事件 |
| `下载 & Range` | 流式下载，字节级 Range / 条件请求（If-Match 等） |
| `TUS /uploads/*` | 分片断点续传、ticket 复用、暂存回收、磁盘水位（>90% → 507） |
| `WebDAV /dav/*` | 标准 WebDAV + PUT 走定稿（≤100MB） |
| `SSE /sync/events` | 实时变更推送 |
| `cursor /changes` | 游标增量拉取 |
| `GET /metrics` | Prometheus 监控指标（默认仅回环/可信代理） |
| `GET /healthz` | 健康检查 |
| `/admin/*` | 内嵌管理后台（Go embed） |

## 9. 架构红线（节选）

- 内核包不得依赖 HTTP/API 层（R-01 家族）；
- 全局加锁顺序固定：spaces 行 → files 行 → file_objects（advisory + 行锁，哈希升序）；
- OAuth / 密钥一律进环境变量，不落版本库；
- 巡检（patrol）**只读**：绝不自动修复，防止误判被放大成数据损坏；
- 配额对账、对象巡检、变更流清理均为后台受控任务，不做无上限扩展。
